# 정산 데이터 고해상도와 조회 성능 개선

## 데이터 고해상도란 무엇인가

여기서 해상도는 데이터가 얼마나 세밀한지를 뜻한다.

기존 시스템은 가맹점과 정산일을 기준으로 거래를 합산해 저장했다.


| 가맹점   | 정산일        | 거래 건수  | 결제 합계       | 수수료 합계   |
| ----- | ---------- | ------: | -----------: | --------: |
| 가맹점 A | 2026-09-23 | 1,000건 | 30,000,000원 | 900,000원 |


개편된 시스템은 같은 결과를 거래 단위로 저장한다.


| 거래 ID | 가맹점 | 정산일        | 결제 금액   | 수수료  |
| ----- | --- | ---------- | -------: | ----: |
| T-001 | A   | 2026-09-23 | 10,000원 | 300원 |
| T-002 | A   | 2026-09-23 | 20,000원 | 600원 |
| T-003 | A   | 2026-09-23 | 30,000원 | 900원 |
| ...   | ... | ...        | ...     | ...  |


```text
낮은 해상도: 1,000개 거래 → 집계 데이터 1건
높은 해상도: 1,000개 거래 → 거래별 데이터 1,000건
```

거래별 데이터는 오류 추적과 재집계에 유리하지만, 저장되는 행의 수가 크게 증가한다. 데이터 고해상도 문제란 이렇게 세밀한 데이터를 보존하면서 발생하는 **저장 공간과 조회 성능 문제**를 말한다.

## 문제 1: 조회해야 하는 데이터가 너무 많아진다

기존에는 정산일별 합계 한 건만 읽으면 됐다.

```sql
SELECT payment_amount, fee_amount
FROM daily_settlement_summary
WHERE merchant_id = 'A'
  AND settlement_date = '2026-09-23';
```

거래 단위로 저장하면 같은 결과를 얻기 위해 많은 행을 읽고 실시간으로 합산해야 한다.

```sql
SELECT
    SUM(payment_amount),
    SUM(fee_amount)
FROM settlement_result
WHERE merchant_id = 'A'
  AND settlement_date = '2026-09-23';
```

거래량이 늘수록 다음 비용도 커진다.

- 검색 대상 행 탐색
- 디스크 I/O
- 합계 계산
- 정렬과 그룹화
- 인덱스 유지

추적 가능성을 얻은 대신 저장 효율과 조회 속도라는 새로운 문제가 생긴 것이다.

## 개선 1: 날짜 기준으로 테이블을 물리적으로 나눈다

정산 업무의 대부분은 정산일을 기준으로 데이터를 조회한다.

```sql
WHERE settlement_date = '2026-09-23'
```

이 특성에 맞춰 `settlement_date`를 기준으로 Range 파티셔닝을 적용한다.

```sql
CREATE TABLE settlement_result (
    transaction_id VARCHAR(50),
    merchant_id VARCHAR(50),
    settlement_date DATE,
    payment_amount DECIMAL(18, 2),
    fee_amount DECIMAL(18, 2)
)
PARTITION BY RANGE (settlement_date);
```

개념적으로 데이터는 다음과 같이 나뉜다.

```text
settlement_result
├── 2026년 7월 파티션
├── 2026년 8월 파티션
├── 2026년 9월 파티션
└── 2026년 10월 파티션
```

9월 23일 데이터를 조회할 때 DB는 전체 테이블이 아니라 9월 파티션만 확인할 수 있다. 이를 파티션 프루닝이라고 한다.

```text
파티셔닝 전: 전체 기간의 데이터 탐색
파티셔닝 후: 조건에 해당하는 날짜 파티션만 탐색
```

파티셔닝은 데이터를 삭제하는 것이 아니라, 자주 사용하는 조회 조건에 맞춰 물리적인 검색 범위를 줄이는 방법이다.

## 개선 2: 정산일을 선두로 하는 복합 인덱스를 만든다

다음과 같은 조회가 자주 발생한다고 가정하자.

```sql
SELECT *
FROM settlement_result
WHERE settlement_date = '2026-09-23'
  AND merchant_id = 'M-100';
```

정산일과 가맹점 ID를 조합한 인덱스를 만들 수 있다.

```sql
CREATE INDEX idx_settlement_date_merchant
    ON settlement_result (settlement_date, merchant_id);
```

복합 인덱스는 컬럼 순서가 중요하다.

```text
(settlement_date, merchant_id)
         ↑
     선두 컬럼
```

대부분의 조회가 정산일을 포함한다면 정산일을 첫 번째 컬럼으로 두어 날짜별 탐색 범위를 먼저 좁힐 수 있다.

```text
전체 데이터
   ↓ 정산일로 범위 축소
2026-09-23 데이터
   ↓ 가맹점으로 범위 축소
가맹점 M-100 데이터
```

모든 컬럼에 인덱스를 추가하면 쓰기 성능과 저장 공간이 나빠진다. 따라서 실제 조회 패턴을 기준으로 필요한 인덱스만 선택해야 한다.

## 파티셔닝과 인덱스의 역할 차이

두 방법은 비슷해 보이지만 역할이 다르다.


| 구분   | 파티셔닝              | 인덱스                  |
| ---- | ----------------- | -------------------- |
| 목적   | 검색할 물리적 데이터 범위 축소 | 범위 안에서 원하는 행을 빠르게 탐색 |
| 적용 예 | 조회 대상 월 선택        | 날짜와 가맹점에 해당하는 위치 탐색  |
| 비유   | 원하는 책장이 있는 층 선택   | 책장의 색인으로 책 위치 검색     |


```text
날짜 파티셔닝으로 대상 파티션 선택
                 ↓
복합 인덱스로 파티션 안의 행 탐색
```

## 남은 문제: 실시간 집계 비용

파티셔닝과 인덱스를 적용해도 다음과 같은 집계 자체의 비용은 사라지지 않는다.

```sql
SELECT
    merchant_id,
    SUM(payment_amount),
    SUM(fee_amount)
FROM settlement_result
WHERE settlement_date = '2026-09-23'
GROUP BY merchant_id;
```

인덱스는 필요한 데이터를 빨리 찾게 해주지만, 수백만 건을 더하고 그룹화하는 계산까지 없애주지는 않는다.

```text
인덱스: 계산할 행을 빠르게 찾음
집계: 찾은 행을 실제로 읽고 더해야 함
```

사용자가 화면을 열 때마다 같은 합계를 반복해서 계산하면 응답 시간이 길어지고 운영 DB에도 부하가 생긴다.

## 개선 3: 조회 전용 테이블을 만든다

서비스의 주요 조회 패턴에 맞춰 미리 가공한 조회 전용 테이블을 추가한다.

원본 테이블은 거래 단위 데이터를 보존한다.

```text
settlement_result
├── T-001 / 가맹점 A / 결제 10,000원 / 수수료 300원
├── T-002 / 가맹점 A / 결제 20,000원 / 수수료 600원
└── T-003 / 가맹점 A / 결제 30,000원 / 수수료 900원
```

조회 전용 테이블에는 화면에서 자주 사용하는 형태로 집계한 결과를 저장한다.


| 가맹점 | 정산일        | 결제 합계   | 수수료 합계 | 지급 합계   |
| --- | ---------- | -------: | ------: | -------: |
| A   | 2026-09-23 | 60,000원 | 1,800원 | 58,200원 |


```text
거래 단위 원본 데이터
        ↓ 배치 또는 이벤트로 집계
조회 전용 데이터
        ↓
서비스 화면에서 빠르게 조회
```

이 구조에서는 역할이 나뉜다.


| 저장소       | 역할                    |
| --------- | --------------------- |
| 원본 정산 테이블 | 정확한 거래별 결과와 추적 가능성 보존 |
| 조회 전용 테이블 | 자주 사용하는 화면에 빠르게 응답    |


조회에 필요한 인덱스를 조회 전용 테이블에 집중할 수 있으므로, 원본 테이블의 배치 쓰기 성능에 미치는 영향도 줄일 수 있다.

## 조회 전용 테이블을 무한정 만들 수는 없다

핵심 서비스 화면은 조회 조건이 비교적 고정돼 있다.

```text
정산일별 지급액
가맹점별 정산 내역
결제수단별 수수료
```

이런 조회는 전용 테이블로 관리하기 좋다. 반면 어드민에서는 다음과 같이 조회 조건이 자주 달라진다.

```text
특정 기간 + 해외 결제 + 부분 취소 + 특정 수수료 계약
특정 가맹점 그룹 + 체크카드 + 지급 보류 상태
상품군 + 결제수단 + 계약 버전별 집계
```

요구사항마다 조회 전용 테이블을 만들면 다음 문제가 생긴다.

- 테이블 수 증가
- 집계 배치 증가
- 데이터 동기화 관리 비용 증가
- 새로운 조건이 추가될 때마다 개발 필요
- 사용 빈도가 낮은 조회를 위해 운영 복잡도 증가

## 개선 4: 핵심 조회와 분석성 조회를 분리한다

조회 성격에 따라 역할을 나눴다.

```text
거래 단위 정산 데이터
├── 핵심 서비스 조회
│   └── 조회 전용 테이블
└── 복잡하고 다양한 어드민 조회
    └── 데이터 서빙 플랫폼
```


| 조회 유형     | 처리 방식             | 중요한 가치           |
| --------- | ----------------- | ---------------- |
| 핵심 서비스 조회 | 직접 관리하는 조회 전용 테이블 | 일정하고 빠른 응답 속도    |
| 어드민·분석 조회 | 고성능 데이터 서빙 플랫폼    | 다양한 조건을 수용하는 유연성 |


모든 조회를 하나의 DB 구조로 해결하려 하지 않고, 응답 속도가 중요한 정형 조회와 유연성이 중요한 비정형 조회를 분리한 것이다.

## 전체 흐름

```text
거래 단위 저장으로 추적 가능성 확보
              ↓
       데이터양과 집계 비용 증가
              ↓
날짜 파티셔닝으로 검색 범위 축소
              ↓
복합 인덱스로 탐색 경로 단축
              ↓
조회 전용 테이블로 반복 집계 제거
              ↓
복잡한 어드민 조회는 데이터 플랫폼에 위임
```
