# 오래 운영할 Open API 생태계 설계

Open API는 엔드포인트 몇 개를 외부에 공개하는 작업이 아니다. 한 번 연동한 고객은 API를 수년간 사용하므로, 인터페이스뿐 아니라 문서, 테스트 환경, 보안, 버전 관리와 조직의 운영 방식까지 하나의 제품으로 설계해야 한다.

Open API의 핵심 요소를 다음 다섯 가지로 정의한다.

1. 인터페이스
2. 외부 생태계와 개발자 경험
3. 보안
4. 안정성
5. 내부 생태계

이 가운데 안정성을 제외한 네 가지 요소를 설명한다.

---

# 1. 예측 가능한 인터페이스

## 리소스를 중심으로 API를 설계한다

경로는 동작보다 리소스를 표현하고, 버전과 리소스 ID의 위치를 일관되게 유지한다.

```text
/{version}/{resource}/{resourceId}

/v1/payments/{paymentKey}
```

리소스의 고유 ID는 경로에 두되, 검색이나 필터 조건은 HTTP 메서드에 맞게 분리한다.

- `GET`: query parameter
- `POST`: JSON body

이 규칙이 일관되면 개발자는 문서를 모두 외우지 않아도 URL과 요청 형식만 보고 API의 역할을 예측할 수 있다.

## 도메인 객체를 재사용한다

관련 필드를 평평하게 나열하기보다 의미 있는 객체로 묶는다.

```json
{
  "paymentKey": "payment-key",
  "card": {
    "company": "현대",
    "number": "0000********000"
  },
  "cashReceipt": null
}
```

결제 승인, 조회, 취소처럼 같은 도메인을 다루는 API는 가능한 한 동일한 객체를 사용한다. 이렇게 하면 다음 효과를 얻는다.

- 새 API를 배울 때의 인지 비용 감소
- 클라이언트의 중복 DTO와 파싱 로직 감소
- 필드 존재 여부를 객체 단위로 판단 가능
- API와 웹훅 사이의 데이터 모델 재사용

## 사람이 이해할 수 있는 값을 제공한다

`SC0010`, `11` 같은 내부 코드는 기계가 처리하기 쉽지만 의미를 파악하려면 별도의 코드표가 필요하다. 외부 API에서는 의미가 드러나는 값을 제공하고, 언어별 표현이 필요하면 `Accept-Language` 같은 표준 헤더를 활용할 수 있다.

다만 자연어 값을 프로그램의 안정적인 식별자로 사용하면 번역이나 문구 변경이 호환성을 깨뜨릴 수 있다. 실제 설계에서는 다음 두 값을 분리하는 방식도 고려한다.

```json
{
  "code": "HYUNDAI_CARD",
  "displayName": "현대"
}
```

## 오류는 기계와 사람 모두가 처리할 수 있어야 한다

HTTP 상태 코드는 오류의 큰 범주를 표현하고, 응답 본문은 서비스가 정의한 상세 원인을 전달한다.

```json
{
  "code": "INVALID_CARD_COMPANY",
  "message": "유효하지 않은 카드사입니다."
}
```

- 클라이언트 프로그램은 `code`로 분기한다.
- 사용자 화면이나 로그는 `message`를 활용한다.
- 호출자는 HTTP 상태 코드만으로 알 수 없는 원인을 확인한다.

오류 코드 역시 공개 계약이므로 이름 변경과 삭제에는 버전 호환성 정책이 필요하다.

# 2. 비동기 결과는 웹훅으로 전달한다

처리 완료 시점을 예측하기 어려운 작업에서 클라이언트가 응답을 계속 기다리게 하면 연결과 자원을 낭비한다. 서버는 요청 접수 여부를 먼저 응답하고, 처리가 끝나면 웹훅으로 결과를 알릴 수 있다.

```text
가맹점 → 결제 요청 → 결제 서버
가맹점 ← 요청 접수 ← 결제 서버

        비동기 처리

가맹점 ← 완료 웹훅 ← 결제 서버
```

웹훅을 설계할 때는 네 가지를 결정해야 한다.

## 이벤트 타입

이벤트의 의미와 payload 구조를 구분할 수 있는 안정적인 식별자가 필요하다.

```text
PAYMENT_STATUS_CHANGED
CANCEL_STATUS_CHANGED
```

## Payload

웹훅의 `data`에는 API에서 사용한 리소스 객체를 재사용한다. 동일한 결제를 API와 웹훅이 서로 다른 구조로 표현하면 클라이언트에 별도 파싱과 변환 코드가 생긴다.

```json
{
  "eventType": "PAYMENT_STATUS_CHANGED",
  "createdAt": "2026-09-23T10:00:00+09:00",
  "data": {
    "paymentKey": "payment-key",
    "status": "DONE"
  }
}
```

## 수신 엔드포인트

가맹점이 이벤트 타입별로 엔드포인트를 나눌 수 있게 하면 서로 다른 payload와 처리 실패를 독립적으로 관리할 수 있다.

## 실패와 재전송

웹훅은 네트워크나 수신 서버 장애로 실패할 수 있다. 즉시 반복 전송하면 장애 중인 서버의 부하를 더 키우므로 지수 백오프를 적용한다.

```text
1차 실패 → 잠시 대기 → 2차 실패 → 더 길게 대기 → 재시도
```

자동 재시도만으로 해결되지 않는 상황을 위해 전송 이력 조회와 수동 재전송 기능도 제공한다. 수신자는 중복 전송을 전제로 멱등하게 처리해야 한다.

# 3. 개발 전 과정을 제품으로 만든다

좋은 개발자 경험은 문서를 읽는 단계부터 운영 장애를 해결하는 단계까지 이어진다.

```text
문서 탐색 → 샌드박스 체험 → 테스트 연동 → 오류 검증 → 로그 분석 → 운영
```

## 실행 코드와 문서를 동기화한다

수동 문서는 서버 구현과 쉽게 어긋난다. 서버가 `springdoc` 등으로 OpenAPI Specification을 생성하고, 이를 기반으로 문서를 갱신하면 요청·응답, 인증 방식과 엔드포인트를 실제 구현에 가깝게 유지할 수 있다.

자동 생성만으로 좋은 문서가 완성되지는 않는다. 명세가 구조를 보장한다면 기술 문서는 API의 역할, 전체 흐름과 사용 맥락을 설명해야 한다.

## 즉시 실행 가능한 샌드박스를 제공한다

설정이나 키 발급 전에 예제 코드를 수정하고 결과를 볼 수 있으면 개발자가 결제 흐름과 데이터 구조를 빠르게 이해할 수 있다. 문서의 정적 예제를 실행 가능한 학습 환경으로 확장하는 것이다.

## 운영과 유사하지만 격리된 테스트 환경을 제공한다

테스트 결과를 신뢰하려면 라이브 환경과 실행 경로의 차이를 줄여야 한다. 토스페이먼츠 사례는 동일한 코드베이스를 사용하면서 Spring Profile로 외부 결제 원천사 호출만 Mock으로 대체한다.

```text
API Key
  ├── 테스트 키 → 테스트 서버 → Mock 원천사
  └── 라이브 키 → 라이브 서버 → 실제 원천사
```

게이트웨이는 API 키를 기준으로 요청을 분기하고, 테스트 서버와 라이브 서버를 분리해 테스트 트래픽이 운영 환경에 영향을 주지 않게 한다.

## 실패도 테스트할 수 있게 한다

정상 흐름만 검증해서는 운영 장애에 대비할 수 없다. 테스트 전용 헤더에 오류 코드를 지정해 원하는 실패 응답을 재현하면 예외 처리와 사용자 안내를 출시 전에 검증할 수 있다.

```http
TossPayments-Test-Code: INVALID_CARD_EXPIRATION
```

이 기능은 테스트 환경에서만 허용하고, 재현 가능한 오류 목록과 실제 응답 계약을 문서화해야 한다.

## 호출자가 스스로 진단할 수 있게 한다

개발자센터에서 요청·응답의 헤더와 본문, 오류 원인과 해결 방법을 조회할 수 있으면 고객 문의 없이 문제를 해결할 수 있다. 단, 로그 화면에서는 API 키, 카드 정보와 개인정보를 마스킹하고 접근 권한과 보존 기간을 엄격히 관리해야 한다.

도구로 해결하기 어려운 문제에는 TAM(Technical Account Manager) 같은 기술 지원 채널을 제공해 셀프서비스와 사람의 지원을 연결한다.

## 버전으로 기존 계약을 보호한다

새 기능 때문에 필드 타입이나 검증 규칙이 바뀌어도 기존 연동을 깨뜨려서는 안 된다. 요청의 버전에 따라 검증과 응답 생성을 분리하고, 변경점과 마이그레이션 방법을 릴리스 노트로 안내한다.

버전만 늘리는 것으로는 충분하지 않다. 다음 정책도 함께 정해야 한다.

- 호환 변경과 비호환 변경의 기준
- 버전별 지원 기간과 종료 절차
- 사용 중인 버전의 관측 방법
- 새 버전 전환 가이드와 테스트 수단

# 4. 보안을 여러 계층으로 적용한다

## 요청 주체를 인증한다

API 요청에는 가맹점별 API Key를 사용해 호출 주체와 권한을 확인한다. 키는 로그나 클라이언트 코드에 노출하지 않고, 교체와 폐기 절차를 제공해야 한다.

웹훅 수신자는 요청을 보낸 주체를 반대로 검증해야 한다. 서버가 payload를 비밀키로 서명하고 가맹점이 서명을 검증하면 발신자와 데이터 무결성을 확인할 수 있다.

## 전송 구간과 데이터 본문을 보호한다

TLS는 클라이언트와 서버 사이에 암호화된 통신 채널을 만든다. 네트워크에서 패킷을 가로채더라도 요청 내용을 읽기 어렵게 하고, 전송 중 데이터가 바뀌었는지도 검증한다. 예를 들어 사용자가 공용 Wi-Fi에서 결제 API를 호출하더라도 카드 정보와 API Key가 평문으로 노출되는 것을 방지한다.

하지만 TLS가 보호하는 범위는 통신 구간이다. TLS가 로드 밸런서나 API Gateway에서 종료되면 그 뒤의 내부 전달 구간, 애플리케이션 메모리와 로그에서는 복호화된 본문이 보일 수 있다. 중간 시스템에도 원문을 노출하지 않아야 하는 고위험 데이터라면 payload 자체를 추가로 암호화할 수 있다.

토스페이먼츠의 Encryption Mode는 JWT 계열의 JWE(JSON Web Encryption)를 사용한다. JWE는 JSON payload를 암호문으로 만들고 암호화된 데이터의 무결성도 확인할 수 있게 한다. 따라서 중간의 프록시나 로깅 시스템은 암호문만 전달하고, 복호화 키를 가진 최종 애플리케이션만 원문을 읽도록 구성할 수 있다.

```text
가맹점 애플리케이션
  └─ 결제 정보를 JWE로 암호화
       ↓ TLS로 전송
API Gateway
  └─ JWE 암호문을 그대로 전달
       ↓
결제 애플리케이션
  └─ JWE 복호화 후 요청 처리
```

TLS와 JWE는 대체 관계가 아니다. TLS는 연결 전체를 보호하고, JWE는 연결이 끝난 뒤에도 특정 메시지 본문이 암호화된 상태로 남도록 한다.

## `iat`: 요청의 유효 시간을 제한한다

`iat`(Issued At)는 요청이 생성된 시각이다. 서버는 현재 시각과 비교해 허용 범위 안에서 생성된 요청만 처리한다.

```text
현재 서버 시각: 10:00:30
요청의 iat:    10:00:10
허용 범위:     5분
결과:          생성 후 20초가 지났으므로 허용
```

공격자가 과거의 암호화된 결제 요청을 확보해 두었다가 한 시간 뒤 다시 보내면, 내용을 해독하지 못하더라도 동일한 동작을 재실행하려 할 수 있다. 서버는 `iat`가 허용 범위를 벗어났다는 이유로 이 요청을 거부한다.

시간 검증에는 서버와 클라이언트의 시계 차이를 고려한 허용 오차가 필요하다. 허용 범위가 너무 길면 공격 가능 시간이 늘어나고, 너무 짧으면 네트워크 지연이나 시계 오차 때문에 정상 요청까지 실패할 수 있다.

## `nonce`: 같은 요청의 재사용을 탐지한다

`nonce`(Number Used Once)는 요청마다 새로 만드는 일회성 식별자다. 서버는 허용 시간 동안 처리한 nonce를 저장하고, 이미 사용한 값이 다시 들어오면 중복 요청으로 거부한다.

```text
10:00:10  nonce=req-7f31 최초 수신 → 저장 후 처리
10:00:12  nonce=req-7f31 다시 수신 → 이미 사용한 값이므로 거부
```

`iat`만 검사하면 공격자가 허용 시간 안에 같은 요청을 여러 번 전송할 수 있다. `nonce`는 이 짧은 구간의 재전송까지 막는다. 반대로 nonce만 영구 저장하면 저장 공간이 계속 증가하므로 일반적으로 `iat`의 허용 시간이 끝날 때 nonce 기록도 만료시킨다.

```text
TLS    → 네트워크 통신 구간의 기밀성과 무결성 보호
JWE    → 개별 요청·응답 본문을 암호화하고 무결성 확인
iat    → 너무 오래된 요청을 거부해 재사용 가능 시간 제한
nonce  → 허용 시간 안에서도 같은 요청이 두 번 처리되는 것을 방지
```

예를 들어 공격자가 정상적인 10만 원 결제 요청의 암호문을 탈취해 그대로 다시 전송한다고 가정하자.

1. TLS는 최초 전송 중 암호문 자체가 탈취될 가능성을 줄인다.
2. JWE 때문에 암호문을 얻더라도 결제 금액이나 가맹점 정보를 읽거나 임의로 변경하기 어렵다.
3. 오래 지난 뒤 전송하면 서버가 `iat`를 검사해 거부한다.
4. 허용 시간 안에 즉시 재전송해도 서버가 중복 `nonce`를 발견해 거부한다.

이 방어는 결제의 비즈니스 멱등성을 완전히 대신하지 않는다. 네트워크 오류로 클라이언트가 정상 요청을 다시 보내는 경우도 있으므로, 결제 서버는 별도의 주문 ID나 멱등성 키를 기준으로 같은 결제가 중복 승인되지 않도록 보장해야 한다.

애플리케이션 암호화는 키 관리와 장애 대응 비용을 늘리므로 데이터 민감도와 위협 모델에 따라 적용한다.

## Rate Limiting으로 피해 범위를 제한한다

비정상적인 반복 요청에는 `429 Too Many Requests`를 반환한다. 이는 자원 고갈을 막을 뿐 아니라 API 키가 유출됐을 때 대량 결제나 취소가 실행되는 속도를 제한한다.

호출자는 재시도 시 `Retry-After`와 지수 백오프를 따르고, 제공자는 가맹점·키·엔드포인트별 정책과 한도를 명확히 알려야 한다.

# 5. 조직 내부에서 품질을 표준화한다

여러 팀이 각 도메인의 API를 개발하더라도 외부 고객에게는 하나의 서비스로 보인다. 인증, 응답, 오류와 문서 규칙을 팀마다 직접 구현하면 차이가 생기고 유지 비용도 커진다.

## 공통 라이브러리

반복되는 규약을 내부 라이브러리로 제공한다.

```text
Open API 공통 라이브러리
├── 인증과 권한
├── API 버전 처리
├── 표준 응답과 오류
├── 문서 자동화
├── 암호화
└── 공통 코드와 타입
```

각 팀은 선언적인 애너테이션과 공통 응답 타입으로 규약을 적용하고 비즈니스 로직에 집중할 수 있다. 공통 라이브러리 자체도 호환성, 배포 주기와 마이그레이션 비용을 관리해야 한다.

## API 위원회

공통 라이브러리가 기술적 강제 장치라면 위원회는 기준을 합의하고 발전시키는 운영 장치다. 새 API가 설계·보안·테스트·릴리스 기준을 지키는지 검토하고, 반복되는 문제를 가이드와 자동화로 환류한다.

위원회가 단순 승인 병목이 되지 않게 다음과 같이 운영할 수 있다.

- 체크리스트와 예시를 문서로 공개한다.
- 정적 검사로 확인할 항목은 CI에서 자동화한다.
- 사람은 도메인 의미와 호환성처럼 자동화하기 어려운 판단에 집중한다.
- 예외 결정과 근거를 기록해 다음 설계에 재사용한다.

# 적용 체크리스트

## 인터페이스

- 경로가 리소스 중심이며 명명 규칙이 일관적인가?
- 동일 도메인의 API와 웹훅이 같은 객체를 재사용하는가?
- HTTP 상태 코드와 서비스 오류 코드의 역할이 구분되는가?
- 웹훅 중복 수신을 안전하게 처리할 수 있는가?
- 재시도 정책과 수동 복구 수단이 있는가?

## 개발자 경험

- 문서와 서버 명세가 자동으로 동기화되는가?
- 실제 결제 없이 전체 흐름을 검증할 수 있는가?
- 운영과 테스트 트래픽이 격리되는가?
- 주요 오류를 의도적으로 재현할 수 있는가?
- 호출자가 요청·응답과 해결 방법을 직접 확인할 수 있는가?
- 비호환 변경을 새 버전으로 분리하고 이전 절차를 안내하는가?

## 보안과 운영

- API Key의 발급, 권한, 교체와 폐기 절차가 있는가?
- 웹훅 서명과 Replay Attack 방어를 적용했는가?
- 민감도에 맞는 전송 및 payload 암호화를 사용하는가?
- Rate Limit의 단위, 한도와 재시도 규칙이 명확한가?
- 공통 규칙을 라이브러리와 자동 검사로 강제하는가?
- 조직 차원의 API 설계 검토와 예외 기록 절차가 있는가?

## 핵심 정리

오래 유지되는 Open API의 품질은 개별 엔드포인트가 아니라 생태계 전체에서 결정된다.

```text
예측 가능한 계약
      +
직접 학습·검증·진단할 수 있는 개발 환경
      +
계층화된 보안
      +
조직 차원의 표준화
      =
오랫동안 신뢰할 수 있는 Open API
```

API를 외부에 공개하는 순간 인터페이스는 장기 계약이 된다. 따라서 구현 속도보다 변경 가능성과 호환성, 호출자의 운영 경험까지 함께 설계해야 한다.
