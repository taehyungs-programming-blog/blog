# 레거시 결제 원장을 확장 가능한 시스템으로 전환하기

## 기존 결제 원장의 문제

결제 원장은 결제, 취소, 환불 내역을 기록하고 정산과 회계의 기초 데이터를 제공하는 핵심 시스템이다. 하지만 20년 이상 운영된 레거시 원장에는 다음 문제가 누적되어 있었다.

예를 들어 고객이 쇼핑몰에서 100,000원을 결제한 뒤 30,000원만 부분 취소했다고 가정하자. 결제 원장은 최소한 다음 사실을 잃지 않고 설명할 수 있어야 한다.

```text
10:00 카드 승인       +100,000원
11:00 부분 취소        -30,000원
현재 유효한 결제 금액   70,000원
```

이 기록은 고객에게 보여주는 결제 상태뿐 아니라 가맹점 정산액과 회계 장부를 계산하는 기준이 된다.

### 결제수단마다 데이터 구조가 다르다

카드는 전체 취소와 부분 취소를 서로 다른 테이블에 저장했지만 계좌이체는 하나의 테이블에 모든 취소 내역을 기록했다. 테이블 이름과 실제 저장 데이터가 일치하지 않는 경우도 있었다.

```text
카드 전체 취소   → card_cancel
카드 부분 취소   → card_partial_cancel
계좌이체 취소    → refund
```

개발자는 단순히 “취소 내역을 조회한다”는 기능을 만들 때도 결제수단을 먼저 구분하고 서로 다른 테이블을 조합해야 한다. `refund`라는 이름만 보고 모든 환불이 저장된다고 판단하면 카드 취소가 조회에서 빠질 수 있다.

이런 구조에서는 신규 개발자가 데이터의 의미를 파악하기 어렵고, 비즈니스 로직을 변경할 때 누락이나 장애가 발생할 가능성이 커진다.

### 여러 도메인이 하나의 테이블을 공유한다

결제, 취소, 정산, 회계 도메인이 동일한 원장 테이블을 직접 사용했다. 같은 컬럼을 도메인마다 다른 의미로 해석하기도 했다.

```text
원장 테이블 변경
   ├─ 결제 영향 분석
   ├─ 취소 영향 분석
   ├─ 정산 영향 분석
   └─ 회계 영향 분석
```

컬럼 하나를 변경해도 여러 팀이 함께 영향도를 확인해야 하므로 서비스의 확장 속도가 느려졌다.

### 결제와 결제수단이 1:1로 묶여 있다

기존 구조에서는 하나의 결제에 하나의 결제수단만 연결할 수 있었다. 따라서 카드와 계좌이체를 함께 사용하는 복합결제나 여러 사용자가 금액을 나누어 내는 더치페이를 구현하기 어려웠다.

## 신규 원장을 별도로 구축한다

기존 Oracle DB에 테이블을 계속 추가하는 대신 MySQL 기반의 신규 원장을 독립적으로 구축했다.

- 결제팀 전용 DB를 사용해 다른 팀의 작업으로 인한 장애 위험을 줄인다.
- Oracle과 MyBatis 대신 주요 개발 스택인 MySQL과 JPA로 통일한다.
- 독립된 환경에서 새로운 구조와 기술을 유연하게 실험한다.

## 핵심 설계 1: 데이터 구조를 통일한다

모든 결제 승인은 공통 `approve` 테이블에 저장하고, 결제수단별 부가 정보만 별도 테이블에 저장한다.

```text
approve
   ├─ card_detail
   ├─ bank_transfer_detail
   └─ virtual_account_detail
```

공통 데이터와 결제수단별 데이터를 분리하면 새로운 결제수단을 추가하더라도 전체 원장 구조를 크게 바꾸지 않아도 된다.

예를 들어 카드로 50,000원을 승인했다면 공통 승인 정보와 카드 전용 정보를 다음처럼 나눌 수 있다.


| 저장 위치         | 주요 데이터                              |
| ------------- | ----------------------------------- |
| `approve`     | 승인 ID, 결제 ID, 금액 50,000원, 승인 시각, 상태 |
| `card_detail` | 카드사, 할부 개월, 카드 승인 번호                |


간편결제가 새로 추가되면 `approve` 구조는 그대로 사용하고 `easy_pay_detail` 같은 상세 테이블만 추가할 수 있다.

### 변경 대신 새로운 이력을 추가한다

기존에는 취소가 발생하면 기존 데이터를 `UPDATE`했다. 신규 원장은 승인과 취소를 새로운 행으로 기록하는 INSERT-only 방식을 사용한다.

```text
기존 방식: 승인 행 UPDATE → 취소 상태
신규 방식: 승인 행 INSERT → 취소 행 INSERT
```

100,000원 승인 후 30,000원을 부분 취소하는 경우를 비교하면 차이가 더 분명하다.

**UPDATE 방식**


| 결제 ID | 승인 금액    | 취소 금액   | 상태    |
| ----- | --------: | -------: | ----- |
| P-100 | 100,000원 | 30,000원 | 부분 취소 |


현재 상태는 알 수 있지만 언제 어떤 순서로 금액이 변경됐는지 알려면 별도의 이력 테이블이나 로그가 필요하다.

**INSERT-only 방식**


| 원장 ID | 결제 ID | 유형    | 금액        | 발생 시각 |
| ----- | ----- | ----- | ---------: | ----- |
| L-1   | P-100 | 승인    | +100,000원 | 10:00 |
| L-2   | P-100 | 부분 취소 | -30,000원  | 11:00 |


두 행의 합계인 70,000원이 현재 유효 금액이며, 원본 행을 수정하지 않아도 전체 변화 과정을 재현할 수 있다.

이 방식은 다음과 같은 장점이 있다.

- 과거 상태와 변경 이력을 추적할 수 있다.
- 데이터의 불변성을 유지할 수 있다.
- 같은 행을 동시에 수정하면서 발생하는 데드락 위험을 줄일 수 있다.

## 핵심 설계 2: 도메인 간 결합을 낮춘다

정산이나 회계 시스템이 결제 원장 DB를 직접 조회하지 않도록 변경했다. 결제가 발생하면 Kafka 이벤트를 발행하고, 각 도메인은 필요한 이벤트를 구독해 자신의 데이터를 처리한다.

```text
결제 원장
   ↓ Kafka 이벤트
   ├─ 정산
   ├─ 회계
   └─ 기타 후속 처리
```

각 도메인은 원장의 테이블 구조가 아니라 이벤트 계약에만 의존한다. 원장 변경이 다른 시스템에 직접 전파되지 않으며 팀별 병렬 개발도 쉬워진다.

여기서 DB를 직접 조회하지 않는다는 것은 DB를 사용하지 않는다는 뜻이 아니다.
정산과 회계 시스템이 **결제 도메인이 소유한 DB를 직접 읽지 않는다**는
뜻이다. 각 도메인은 자신의 업무에 필요한 데이터를 자신의 DB에 저장한다.

기존에는 정산 시스템이 결제 원장 DB에 접속해 결제 테이블과 카드 승인
테이블을 조인했다고 가정해 보자.

```text
정산 시스템
   ↓ 결제 테이블과 카드 승인 테이블 직접 조회
결제 원장 DB
```

이 구조에서는 결제팀이 테이블 이름이나 컬럼을 변경하면 정산 시스템의
쿼리도 함께 수정해야 한다. 정산 시스템이 결제 도메인의 내부 구현에
의존하기 때문이다.

Kafka를 사용하면 결제 서비스는 결제 결과를 자신의 원장 DB에 기록한 뒤
`PaymentApproved` 이벤트를 발행한다. 정산과 회계 시스템은 이 이벤트를
구독하고, 필요한 형태로 가공해 각자의 DB에 저장한다.

```text
결제 서비스
   ├─ 결제 원장 DB에 결제 기록 저장
   └─ PaymentApproved 이벤트 발행
      (결제 ID, 가맹점 ID, 승인 금액, 결제 시각, 결제수단)
                    ↓
                  Kafka
          ┌─────────┴─────────┐
       정산 시스템          회계 시스템
   가맹점 ID와 승인 금액    결제 ID, 승인 금액,
   결제 시각을 읽음         결제수단을 읽음
          ↓                    ↓
   지급 예정액과 지급일     매출과 미지급금
   계산 후 정산 DB 저장     분개 후 회계 DB 저장
```

예를 들어 정산 시스템은 가맹점 ID, 승인 금액, 결제 시각을 읽는다.
이 데이터로 가맹점별 수수료를 차감하고 지급 예정액과 지급일을 계산해
정산 DB에 저장한다.

회계 시스템은 결제 ID, 승인 금액, 결제수단을 읽는다. 이 데이터로 매출과
카드사 미수금 또는 미지급금 같은 회계 분개를 생성해 회계 DB에 저장한다.
두 시스템은 같은 이벤트를 받지만 자신의 업무에 필요한 필드만 사용한다.
둘 다 DB를 사용하더라도 결제 원장 DB의 테이블 구조는 알 필요가 없다.

즉, 의존성이 다음과 같이 바뀐다.

```text
결제 DB 스키마에 대한 의존
          ↓
PaymentApproved 이벤트 계약에 대한 의존
```

예를 들어 `PaymentApproved` 이벤트에 결제 ID, 가맹점 ID, 승인 금액이 담겨 발행되면 각 시스템은 같은 사건을 서로 다르게 사용한다.

```text
PaymentApproved(P-100, 가맹점-A, 100,000원)
   ├─ 정산: 수수료를 제외한 지급액 계산
   ├─ 회계: 매출과 미지급금 분개 생성
   └─ 알림: 고객에게 결제 완료 메시지 발송
```

정산 시스템은 카드 상세 테이블의 위치나 컬럼 이름을 몰라도 된다.

## 핵심 설계 3: 결제와 승인을 분리한다

신규 시스템에서는 결제와 승인을 서로 다른 개념으로 정의한다.

- **결제**: 사용할 결제수단이 아직 확정되지 않은 상위 거래
- **승인**: 실제 결제수단으로 처리된 결과

```text
결제 1건
   ├─ 카드 승인 30,000원
   └─ 계좌이체 승인 70,000원
```

하나의 결제에 여러 승인을 연결할 수 있어 복합결제와 더치페이 같은 요구사항을 지원할 수 있다.

예를 들어 100,000원짜리 주문을 포인트와 카드로 나누어 결제할 수 있다.


| 결제 ID | 승인 ID | 결제수단 | 승인 금액   |
| ----- | ----- | ---- | -------: |
| P-200 | A-1   | 포인트  | 20,000원 |
| P-200 | A-2   | 카드   | 80,000원 |


결제 `P-200`의 총액은 두 승인 금액을 더한 100,000원이다. 카드 승인에 실패하면 포인트 승인을 취소하는 등 승인별 상태도 독립적으로 관리할 수 있다.

## 무중단을 위한 점진적 마이그레이션

신규 원장으로 한 번에 전환하지 않고 기존 원장에 먼저 저장한 뒤 신규 원장에 비동기로 적재했다.

```text
결제 요청
   ↓
기존 원장 저장
   ↓ 비동기
신규 원장 저장
```

신규 원장 적재가 실패하더라도 실시간 결제에는 영향을 주지 않도록 예외를 분리하고, 실패 내역은 모니터링과 알림으로 관리했다.

예를 들어 신규 DB가 일시적으로 느려진 상황에서 1,000건의 결제 중 10건을 적재하지 못하더라도 고객의 결제를 실패시키지는 않는다. 기존 원장에는 1,000건을 모두 기록하고, 누락된 10건은 이후 검증 배치가 찾아 신규 원장에 다시 저장한다.

### 서비스 자원을 보호한다

비동기 적재도 실서비스 서버의 CPU와 메모리를 사용한다. 처음에는 작은 ThreadPool로 시작해 트래픽을 점진적으로 늘리며 적정 크기를 찾았다.

ThreadPool이 포화되면 결제 요청을 지연시키는 대신 신규 원장 적재 작업을 포기한다. 누락 데이터는 별도 검증 배치가 나중에 복구한다. 핵심 결제의 가용성을 우선하고 최종 정합성을 사후에 보장하는 선택이다.

### 두 원장의 정합성을 계속 검증한다

RO DB를 읽는 검증 배치를 5분 주기로 실행해 기존 원장에는 있지만 신규 원장에는 없는 데이터를 찾아 재적재했다. 복제 지연을 고려해 최신 데이터에 적절한 시간 여유를 두고 비교했다.

```text
기존 원장 결제 ID: P-301, P-302, P-303
신규 원장 결제 ID: P-301,        P-303
                                  ↓
검증 배치가 P-302를 찾아 신규 원장에 재적재
```

## 수억 건의 과거 데이터 이관

실시간 신규 데이터의 적재가 안정된 뒤 기존 데이터를 신규 원장으로 옮겼다. 대량의 INSERT가 실서비스에 영향을 주지 않도록 다음 방식을 사용했다.

- 마이그레이션 전용 서버를 배포해 실서비스 자원과 분리한다.
- 신규 DB와 같은 AWS 가용 영역에 서버를 배치해 네트워크 지연을 줄인다.
- 단건 저장을 Bulk Insert로 변경한다.
- 반복 조회 데이터는 로컬 메모리에 캐시한다.
- 기존 IDC와 AWS 사이의 네트워크 대역폭을 모니터링하며 처리량을 조절한다.

대규모 마이그레이션은 단순한 데이터 복사가 아니라 DB, 애플리케이션, 네트워크 병목을 함께 제어하는 작업이다.

가령 1억 건을 한 건씩 저장하면 애플리케이션과 DB 사이의 왕복도 1억 번 발생한다. 1,000건씩 묶어 Bulk Insert하면 개념적으로 왕복 횟수를 약 10만 번 수준으로 줄일 수 있다. 실제 성능은 행 크기와 DB 설정 등에 따라 달라지지만, 저장 요청의 고정 비용을 크게 줄인다는 원리는 같다.

## 운영 장애와 복구

신규 기능에 추가된 SELECT 쿼리가 데이터 증가 후 예상과 다른 실행 계획을 사용했다. MySQL 옵티마이저가 인덱스 대신 전체 테이블 스캔을 선택하면서 CPU와 I/O 사용량, 대기 세션이 급증했다.

문제가 직전 배포에서 발생한 것을 확인한 뒤 이전 Docker 이미지로 즉시 롤백했다. 이후 쿼리 힌트를 추가해 의도한 인덱스를 사용하도록 수정했다.

이 사례는 적은 데이터에서 정상적으로 동작하는 쿼리도 데이터가 충분히 쌓이면 다른 실행 계획과 성능을 보일 수 있다는 점을 보여준다.

예를 들어 개발 환경의 1,000건에서는 전체 스캔도 금방 끝난다. 운영 환경의 1억 건에서 같은 방식으로 검색하면 한 요청이 많은 데이터를 읽고, 요청이 몰릴수록 대기 세션이 연쇄적으로 증가할 수 있다. 따라서 운영 데이터 규모를 가정한 실행 계획과 부하 검증이 필요하다.

## 장애로 드러난 정합성 문제

### 기존 원장과 신규 원장이 다르다

DB 부하로 신규 원장 적재 일부가 실패했지만 기존 원장을 정답 데이터로 사용하는 5분 주기 보정 배치가 누락분을 복구했다.

멀티 데이터 소스를 운영할 때는 두 저장소가 항상 같을 것이라고 기대하기보다, 언제든 달라질 수 있다고 가정하고 비교와 복구 수단을 준비해야 한다.

### 외부 결제기관과 상태가 다르다

카드사에 승인 요청을 보낸 뒤 네트워크 타임아웃이 발생하면 카드사에서는 성공했지만 내부 시스템에는 실패로 기록될 수 있다.

```text
1. 기업 → 카드사: 50,000원 승인 요청
2. 카드사: 승인 성공
3. 카드사 → 토스페이먼츠: 성공 응답 전송
4. 네트워크 지연으로 응답 유실
5. 기업: 타임아웃으로 실패 판단
```

이 상태를 방치하면 고객 카드에서는 금액이 승인됐지만 쇼핑몰에는 결제 실패로 표시된다.

이런 거래를 별도로 저장하고 카드사나 은행에 취소 요청을 보내는 망취소 로직으로 양쪽 상태를 일치시킨다.

### 가맹점이 받은 응답과 실제 결과가 다르다

MSA 요청 경로에 있는 서버들의 타임아웃 설정이 서로 달랐다. 승인 서버는 처리를 완료했지만 앞단 서버가 먼저 타임아웃되어 가맹점에는 실패를 반환하는 상황이 발생했다.

승인 서버의 최대 처리 시간을 기준으로 상위 서버들의 타임아웃을 조정해 요청 체인 전체의 설정을 일관되게 맞췄다.

예를 들어 승인 서버가 정상 상황에서도 최대 5초까지 필요할 수 있는데 앞단 서버의 타임아웃이 3초라면, 승인은 4초에 성공해도 가맹점에는 이미 실패가 전달된다. 앞단으로 갈수록 내부 처리 시간을 포함할 수 있도록 타임아웃을 설계해야 한다.

```text
가맹점 요청 제한 8초
   └─ 앞단 서버 제한 7초
       └─ 승인 서버 제한 5초
```

### 이벤트가 누락되거나 중복된다

결제 이벤트는 Outbox 패턴으로 발행하지만, Outbox 저장 실패 때문에 결제 자체를 실패시키지는 않았다. 결제 가용성을 우선했기 때문에 Outbox에도 남지 않은 이벤트가 생길 수 있었다.

누락된 거래는 Elasticsearch와 서버 로컬 디스크의 보조 로그에서 찾아 이벤트를 재발행했다. 이 과정에서 이미 처리된 이벤트가 다시 발행될 수 있으므로 이벤트 헤더에 멱등키를 추가해 소비자가 동일 이벤트를 중복 처리하지 않도록 했다.

예를 들어 정산 시스템이 이벤트 `EVT-100`을 처리해 정산 데이터를 만든 뒤 같은 이벤트를 다시 받았다고 가정하자.

```sql
INSERT INTO processed_event (event_id) VALUES ('EVT-100');
```

`event_id`에 유니크 제약을 두면 두 번째 `EVT-100` 저장은 실패한다. 소비자는 이미 처리한 이벤트임을 확인하고 정산 데이터를 다시 만들지 않는다. 이렇게 재시도와 중복 발행이 발생해도 결과가 한 번 처리한 것과 같도록 만드는 성질이 멱등성이다.
