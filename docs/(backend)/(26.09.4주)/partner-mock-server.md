# 제휴사 연동 테스트를 위한 Mock·Relay 서버 설계

## 배경

여러 제휴사의 API와 연동이 필요한 케이스. 신규 제휴사를 연결한 뒤에는 다음 문제가 반복됐다.

- 제휴사 개발 서버가 불안정하거나 장애가 발생한다.
- 특정 고객 조건과 업무 단계에 맞는 테스트 데이터를 얻기 어렵다.
- 테스트 중 실제 제휴사로부터 유효한 응답을 받기 어렵다.

외부 환경에 의존하면 개발과 QA 일정까지 제휴사의 상태에 영향을 받는다.
이를 해결하기 위해 사용자, 제휴사, 퍼널 단위로 동작을 제어하는 Mock 서버를
구축했다.

## 요구사항

### 기능 요구사항

- 사용자·제휴사·퍼널별로 Mock 사용 여부를 설정한다.
- 동기 응답과 비동기 콜백을 모두 재현한다.
- Mock을 사용하지 않는 요청은 실제 제휴사로 전달한다.
- 개발자와 QA가 설정을 쉽게 조회하고 변경할 수 있어야 한다.

### 설계 제약

- 기존 비즈니스 로직을 수정하지 않는다.
- Mock 처리에 필요한 값은 커스텀 헤더로 전달한다.
- 다른 제휴사 연동 서비스도 재사용할 수 있어야 한다.
- Mock 기능은 개발 환경에서만 활성화한다.

## 전체 요청 흐름

```text
클라이언트
    │ 사용자 ID, 요청 ID가 담긴 요청
    ▼
신용대출 서비스
    │ 개발 환경에서 커스텀 헤더 주입
    ▼
Mock·Relay 서버
    ├─ Mock 설정 있음 ──> 응답 생성 또는 콜백 예약
    └─ Mock 설정 없음 ──> 실제 제휴사 호출 ──> 응답 중계

제휴사 비동기 콜백
    └─ API Gateway ──> Mock 서버 ──> 신용대출 서비스
```

Mock 서버가 요청 경로에 항상 존재하되, 설정에 따라 가짜 응답을 만들거나
실제 요청을 중계한다. 따라서 호출하는 서비스의 핵심 로직은 Mock 사용 여부를
알 필요가 없다.

## 1. 커스텀 헤더로 테스트 문맥 전달

신용대출 서비스가 Mock 서버에 요청을 보낼 때, Mock 서버는 **어느 사용자의
어떤 요청인지** 알아야 알맞은 시나리오를 고를 수 있다. 그렇다고 모든
비즈니스 메서드와 제휴사 요청 본문에 테스트 전용 값을 추가하면 운영 코드가
Mock 서버에 의존하게 된다.

그래서 테스트 정보는 요청 본문이 아니라 HTTP 헤더로 전달한다.
`RestTemplate`은 `ClientHttpRequestInterceptor`, `WebClient`는
`ExchangeFilterFunction`을 사용한다. 이 구성요소는 외부 요청이 나가기
직전에 사용자 ID와 요청 ID를 자동으로 추가한다.

```text
고객 앱
  │ 가심사 요청
  ▼
신용대출 서비스
  │ 1. 평소와 동일하게 제휴사 요청 생성
  │ 2. HTTP 클라이언트가 헤더를 자동 추가
  ▼
Mock 서버
  │ 3. 헤더로 사용자별 테스트 설정 조회
  ├─ 설정 있음 → 지정된 Mock 응답 반환
  └─ 설정 없음 → 실제 제휴사로 요청 전달
```

이 헤더 주입 기능은 Spring의 `dev` 프로필에서만 활성화한다. 운영에서는
인터셉터나 필터가 등록되지 않으므로 테스트용 헤더를 보내지 않는다.

이 방식의 장점은 다음과 같다.

- 업무 메서드마다 테스트용 인자를 추가하지 않아도 된다.
- 제휴사 호출 코드에 Mock 분기가 퍼지지 않는다.
- 한곳에서 모든 외부 요청에 일관된 문맥을 전달한다.
- 운영 환경에서 테스트용 헤더가 들어가는 위험을 줄인다.

테스트 기능을 비즈니스 인터페이스가 아니라 통신 계층에 격리한 것이
핵심이다.

### 예시: `user-100`의 A은행 가심사를 실패시킨다

QA가 `user-100`의 A은행 가심사 결과를 `심사 거절`로 미리 설정했다고
가정하자.

고객 앱이 보내는 요청은 평소와 같다. 앱은 Mock 사용 여부를 알지 못한다.

```http
POST /loan/pre-screenings
Content-Type: application/json

{
  "partnerId": "bank-a"
}
```

신용대출 서비스는 이 요청을 처리한 뒤 A은행 형식의 요청을 만든다. 개발
환경의 HTTP 인터셉터는 요청이 전송되기 직전에 헤더를 추가한다.

```http
POST /partners/bank-a/pre-screenings
X-Mock-User-Id: user-100
X-Mock-Request-Id: pre-screening-20260927-001

{
  "jobType": "OFFICE_WORKER",
  "annualIncome": 50000000
}
```

Mock 서버는 `X-Mock-User-Id`를 읽고 다음과 같이 판단한다.

```text
사용자: user-100
제휴사: bank-a
업무 단계: 가심사
설정된 결과: 심사 거절
```

따라서 실제 A은행 서버를 호출하지 않고 미리 준비한 거절 응답을 반환한다.

```json
{
  "result": "REJECTED",
  "reasonCode": "INCOME_REQUIREMENT_NOT_MET"
}
```

반대로 `user-200`에게 설정된 시나리오가 없다면 Mock 서버는 동일한 요청을
실제 A은행 개발 서버로 전달한다.

### 인터셉터가 필요한 이유

인터셉터가 없다면 모든 호출부에 다음과 같은 테스트 코드가 들어갈 수 있다.

```kotlin
fun requestPreScreening(
    request: PartnerRequest,
    mockUserId: String?,
    mockRequestId: String?,
): PartnerResponse
```

가심사뿐 아니라 대출 신청, 실행, 상태 조회 메서드에도 같은 인자를 추가해야
한다. 테스트 기능 때문에 운영 인터페이스가 변경되는 것이다.

인터셉터를 사용하면 비즈니스 메서드는 원래 형태를 유지한다.

```kotlin
fun requestPreScreening(request: PartnerRequest): PartnerResponse
```

HTTP 클라이언트가 현재 요청의 사용자 정보를 가져와 헤더에 넣는 책임을
맡는다. 즉, 1번의 핵심은 **Mock 여부를 헤더 하나로 결정한다는 것보다,
테스트 정보 전달 책임을 비즈니스 로직에서 HTTP 통신 계층으로 옮긴 것**이다.

## 2. DB 기반 설정

1번에서 전달한 사용자 ID만으로는 어떤 응답을 반환해야 할지 알 수 없다.
Mock 서버는 DB에서 **제휴사는 어떻게 통신하는지**, **준비된 응답은
무엇인지**, **이 사용자가 어떤 응답을 선택했는지**를 차례로 조회한다.

동작을 코드에 하드코딩하지 않고 세 종류의 데이터로 나눈 이유다.

| 설정 | 책임 |
| --- | --- |
| `partner_metadata` | 동기·비동기 여부, 네트워크, 암호화 등 제휴사 특성 |
| `partner_response` | 제휴사와 퍼널별 응답 본문 및 JSON 구조 |
| `user_status` | 사용자별 Mock 사용 여부, 응답 종류와 지연 시간 |

응답은 대략 `(제휴사, 퍼널, 상태)` 조합으로 선택한다. 같은 API라도 사용자와
테스트 목적에 따라 성공, 거절, 지연 등의 시나리오를 재현할 수 있다.

### 세 설정이 연결되는 과정

```text
요청 헤더
└─ 사용자: user-100

요청 경로
├─ 제휴사: A은행
└─ 업무 단계: 가심사

1. user_status 조회
   └─ user-100 + A은행 + 가심사 = LIMIT_APPROVED

2. partner_metadata 조회
   └─ A은행 가심사는 비동기 응답, 콜백 기본 지연 30초

3. partner_response 조회
   └─ A은행 + 가심사 + LIMIT_APPROVED의 JSON 템플릿

4. 최종 동작
   └─ 접수 응답을 보내고 30초 뒤 한도 승인 콜백 전송
```

각 설정의 책임을 분리했기 때문에 A은행의 통신 방식은 한 번만 정의하고,
사용자마다 어떤 결과를 받을지만 바꿀 수 있다.

### 예시: 두 사용자가 같은 API에서 다른 결과를 받는다

| 사용자 | 제휴사 | 업무 단계 | 시나리오 |
| --- | --- | --- | --- |
| `user-100` | A은행 | 가심사 | 한도 3,000만 원 승인 |
| `user-200` | A은행 | 가심사 | 소득 조건 미달로 거절 |

두 사용자가 완전히 같은 소득 정보를 보내도 Mock 서버는 사용자 설정에 따라
다른 응답을 반환한다.

```text
user-100 → A은행 가심사 → LIMIT_APPROVED 선택 → 3,000만 원 승인
user-200 → A은행 가심사 → INCOME_REJECTED 선택 → 소득 조건 미달
```

QA는 코드를 수정하거나 서버를 다시 배포하지 않고 `user_status`의 선택만
변경해 성공과 실패 화면을 반복해서 테스트할 수 있다.

### 업무 단계별로도 결과를 다르게 설정한다

한 사용자에게 모든 API가 같은 결과를 반환하는 것은 아니다.

```text
user-100 + A은행 + 가심사   → 승인
user-100 + A은행 + 대출 신청 → 거절
user-100 + A은행 + 상태 조회 → 심사 중
```

이를 원문에서는 사용자·제휴사·퍼널 단위 설정이라고 표현한다. 여기서 퍼널은
가심사, 대출 신청, 상태 조회 같은 업무 단계를 의미한다.

## 3. 비동기 콜백 예약

모든 제휴사가 요청 결과를 즉시 반환하는 것은 아니다. 대출 신청을 접수했다는
응답만 먼저 보내고, 심사가 끝난 뒤 토스의 콜백 API로 결과를 보내는 제휴사도
있다. Mock 서버도 이 시간차를 재현해야 비동기 처리 코드를 테스트할 수 있다.

1. 가심사나 대출 신청 요청을 받는다.
2. 사용자 설정 또는 제휴사 메타데이터에서 지연 시간을 가져온다.
3. 실행 시각과 함께 예약 정보를 DB에 저장한다.
4. 주기 작업이 실행 시각이 지난 예약을 조회한다.
5. `ThreadPoolTaskScheduler`가 지정 시각에 콜백을 보낸다.

여러 서버가 같은 예약을 실행하지 않도록 예약 ID별 분산 잠금을 사용한다.
예약 상태도 실행 전에 갱신해 중복 처리 가능성을 낮춘다. 즉, 지연 실행뿐
아니라 다중 인스턴스 환경의 동시성까지 고려한 구조다.

### 예시: 요청 시점에는 결과를 알 수 없다

```text
10:00:00  신용대출 서비스 → Mock 서버: 대출 신청
10:00:00  Mock 서버 → 신용대출 서비스: 접수 완료
10:00:00  신용대출 서비스: 신청 상태를 PENDING으로 저장

10:00:30  Mock 서버 → 신용대출 서비스: 대출 승인 콜백
10:00:30  신용대출 서비스: 신청 상태를 APPROVED로 변경
10:00:30  고객 앱: 승인 결과 확인
```

Mock 서버는 최초 요청을 받을 때 다음 예약을 저장한다.

```text
schedule_id: 501
request_id: loan-application-9001
callback_result: APPROVED
execute_at: 10:00:30
status: WAITING
```

주기 작업이 `execute_at`이 지난 예약을 찾고 콜백 작업을 스케줄러에 넘긴다.
콜백이 성공하면 예약 상태를 완료로 변경한다.

### 분산 잠금이 필요한 이유

Mock 서버가 두 대라면 두 서버가 동시에 `schedule_id=501`을 조회할 수 있다.

```text
잠금이 없는 경우
서버 A → 승인 콜백 전송
서버 B → 승인 콜백 전송
결과   → 같은 신청에 콜백이 두 번 도착

잠금이 있는 경우
서버 A → schedule-501 잠금 획득 → 콜백 전송
서버 B → 잠금 획득 실패 → 처리하지 않음
결과   → 콜백 한 번만 도착
```

따라서 3번은 단순히 응답을 늦추는 기능이 아니다. 실제 제휴사의
`접수 → 대기 → 콜백` 흐름과 다중 서버 환경을 함께 재현하는 기능이다.

## 4. 템플릿을 실제 원장 데이터로 치환

고정 JSON만 반환하면 상품명, 한도, 금리, 거래 ID가 실제 원장과 맞지 않을
수 있다. 그래서 제휴사별 JSON 템플릿에 예약어를 넣는다.

```json
{
  "amount": "{{amount}}",
  "period": "{{period}}",
  "interestRate": "{{interestRate}}",
  "productId": "{{productId}}",
  "id": "{{id}}"
}
```

같은 성공 시나리오라도 사용자와 상품에 따라 값이 달라져야 한다. 제휴사별
응답 구조는 템플릿으로 보존하고, 변하는 값만 실행 시점에 채운다.

생성 과정은 두 단계다.

1. JSON 트리를 재귀 순회하며 한도, 기간, 금리, 상품명 등을 치환한다.
2. 상품명을 기준으로 원장에 대응하는 거래 ID를 찾아 다시 치환한다.

제휴사마다 상품명 필드가 다르므로 해당 필드명도 메타데이터로 관리한다.
이 방식은 서로 다른 JSON 구조를 보존하면서 실제 내부 데이터와 일치하는
응답을 만들 수 있게 한다.

### 예시: 고정 JSON에서 발생하는 문제

가심사 Mock이 항상 다음 값을 반환한다고 가정하자.

```json
{
  "productName": "A은행 직장인 대출",
  "productId": "test-product-1"
}
```

신용대출 서비스의 실제 원장에 `test-product-1`이 없다면 가심사는 성공해도
다음 대출 신청 단계에서 상품을 찾지 못한다. 화면 한 장은 테스트할 수 있지만
전체 업무 흐름은 테스트할 수 없는 Mock 데이터다.

### 예시: 템플릿을 원장 데이터로 바꾸는 과정

Mock 서버는 먼저 시나리오에 저장된 템플릿을 읽는다.

```json
{
  "amount": "{{amount}}",
  "productName": "{{productName}}",
  "productId": "{{productId}}"
}
```

그다음 테스트 대상 원장에서 실제 상품 정보를 찾는다.

```text
상품명: A은행 직장인 신용대출
원장 상품 ID: ledger-product-1234
테스트 한도: 30,000,000원
```

예약어를 실제 값으로 치환한 최종 응답은 다음과 같다.

```json
{
  "amount": 30000000,
  "productName": "A은행 직장인 신용대출",
  "productId": "ledger-product-1234"
}
```

신용대출 서비스는 이 ID를 실제 상품으로 인식한다. 따라서 가심사에서 받은
상품을 선택하고 대출 신청까지 이어지는 통합 테스트가 가능하다.

### 제휴사마다 필드명이 다른 경우

A은행은 상품명을 `productName`, B은행은 `loanGoodsName`에 담을 수 있다.
Mock 서버는 제휴사 메타데이터에 상품명 필드도 저장한다.

```text
A은행 상품명 필드 → productName
B은행 상품명 필드 → loanGoodsName
```

JSON 트리를 재귀적으로 순회하므로 상품 배열이나 중첩 객체 안에 예약어가
있어도 찾아서 바꿀 수 있다.

## 5. Relay로 실서버와 Mock을 한 경로에 통합

사용자에게 선택된 Mock 시나리오가 있으면 가짜 응답을 반환하고, 없으면 실제
제휴사를 호출해 결과를 그대로 전달한다. 제휴사가 보내는 콜백도 API Gateway
라우팅을 통해 Mock 서버가 먼저 받은 뒤 내부 서비스로 중계한다.

이 구조에서는 테스트 대상이 URL을 바꿀 필요 없이 실제 응답과 Mock 응답을
오갈 수 있다. Mock 서버가 단순 스텁이 아니라 외부 연동의 프록시이자 테스트
제어 지점으로 동작한다.

### Relay가 없다면 생기는 문제

일반적인 Mock 서버는 실제 서버와 주소가 다르다.

```text
실제 A은행: https://dev.bank-a.example.com
Mock A은행: https://mock.internal/bank-a
```

이 경우 테스트할 때마다 애플리케이션 설정을 바꾸고 재시작해야 한다. 여러
제휴사 중 일부만 Mock으로 전환하는 것도 번거롭다.

Relay 구조에서는 신용대출 서비스가 항상 Mock 서버 주소만 호출한다.

```text
신용대출 서비스 → Mock 서버 → 설정에 따라 Mock 또는 실제 제휴사 선택
```

### 예시: 한 요청에서 일부 은행만 Mock으로 전환

```text
고객의 대출 비교 요청
├─ A은행 → Mock 설정 있음 → 타임아웃 응답 생성
├─ B은행 → Mock 설정 없음 → B은행 개발 서버 호출
└─ C은행 → Mock 설정 있음 → 한도 2,000만 원 응답 생성
```

한 번의 대출 비교 요청에서 일부 제휴사 장애가 전체 결과에 미치는 영향을
검증할 수 있다. 클라이언트는 제휴사별 URL을 바꾸지 않는다.

### 제휴사에서 들어오는 콜백도 중계한다

요청 방향과 반대로 실제 B은행이 토스에 콜백을 보내는 경우도 있다.

```text
B은행
  → API Gateway
  → Mock 서버
  → 신용대출 서비스의 콜백 API
```

API Gateway가 콜백을 바로 신용대출 서비스로 보내지 않고 Mock 서버를 거치게
한다. Mock 서버는 실제 콜백을 내부 서비스로 그대로 전달한다. 따라서 Mock
콜백과 실제 제휴사 콜백이 동일한 내부 API에 도착한다.

5번의 핵심은 Mock 서버가 가짜 응답만 만드는 것이 아니라, Mock을 사용하지
않는 통신까지 통과시키는 프록시 역할을 한다는 것이다.

## 6. 메신저봇을 운영 인터페이스로 사용

Mock 기능이 좋아도 설정이 복잡하면 QA가 개발자에게 의존한다. 팀에서 이미
사용하는 메신저봇에 다음 기능을 붙여 진입 장벽을 낮췄다.

- 현재 제휴사·퍼널별 설정 조회
- 특정 제휴사·퍼널의 Mock 활성화
- 사용할 응답 시나리오 선택

테스트 인프라의 완성도는 서버 기능뿐 아니라 사용자가 스스로 조작할 수 있는
인터페이스에도 달려 있다는 점을 보여준다.

### 메신저봇이 없을 때

QA가 거절 시나리오를 테스트하려면 개발자에게 다음과 같이 요청해야 한다.

```text
"user-100의 A은행 대출 신청 결과를 거절로 바꿔주세요."
```

개발자는 DB에서 관련 행을 찾고 값을 변경한 뒤 적용 여부를 알려줘야 한다.
테스트 케이스를 바꿀 때마다 같은 과정이 반복된다.

### 예시: QA가 거절 시나리오를 직접 설정한다

```text
1. "Mock 설정" 메뉴 선택
2. 테스트 사용자 user-100 선택
3. A은행 → 대출 신청 선택
4. "소득 조건 미달로 거절" 시나리오 선택
5. 콜백 지연 시간을 10초로 설정
6. 저장
```

메신저봇은 내부적으로 `user_status` 설정을 변경한다. 저장 후 조회 버튼을
누르면 다음과 같은 현재 상태를 보여준다.

```text
[user-100의 Mock 설정]
A은행 / 가심사: 한도 승인
A은행 / 대출 신청: 소득 조건 미달
콜백 지연: 10초
```

QA는 앱에서 `user-100`으로 대출을 신청한다. 10초 뒤 거절 콜백이 도착하면
거절 화면과 안내 문구를 확인한다. 테스트가 끝나면 메신저봇에서 Mock을
비활성화한다.

즉, 6번은 새로운 Mock 로직이 아니다. 2번의 DB 설정을 개발자뿐 아니라 QA도
안전하고 쉽게 변경할 수 있게 만든 관리 화면이다.

## 7. 다른 서비스로 확장하는 모듈 구조

신용대출만 생각하고 하나의 애플리케이션에 모든 코드를 넣으면 보험, 결제 등
다른 제휴사 연동 서비스가 Mock 기능을 사용할 때 코드를 복사해야 한다.
그래서 모든 서비스에 공통인 기능과 서비스마다 다른 기능을 분리했다.

```text
mock-server-api
└── 요청을 받는 진입점

mock-server-base
├── 콜백과 템플릿 치환
└── 공통 Handler 추상화

mock-server-{service}
└── 서비스별 비즈니스 로직

mock-server-{service}-admin
└── 서비스별 관리 기능
```

새 서비스는 전용 모듈만 추가하면 공통 콜백과 치환 기능을 재사용할 수 있다.

각 모듈의 역할을 실제 요청에 대입하면 다음과 같다.

```text
보험 가입 Mock 요청
  │
  ▼
mock-server-api
  └─ URL과 요청을 받아 보험 서비스 Handler로 전달
  │
  ▼
mock-server-insurance
  └─ 보험 가입인지 판단하고 보험 응답 생성 규칙 실행
  │
  ▼
mock-server-base
  ├─ JSON 예약어 치환
  ├─ 콜백 예약
  └─ 실제 보험사로 Relay
```

서비스마다 별도 DB를 사용할 수 있어 Spring Multi DataSource도 지원한다.
Repository 상속, 어노테이션 중복, 동일한 패키지 구조를 고려해 DataSource를
클래스로 명시하는 방식을 선택했다.

설정 파일도 `application-{service}.properties`로 나눈다. 기본 모듈의
`application.properties`가 Spring Cloud Config와 서비스별 설정을 가져와
최종 구성을 완성한다. 설정의 소유 서비스가 분명해지고 모듈 간 영향도
추적하기 쉬워진다.

### 예시: 보험 서비스를 추가한다

신용대출과 보험은 업무 용어와 응답 JSON이 다르다.

```text
신용대출 고유 기능
├─ 가심사
├─ 대출 신청
└─ 대출 실행

보험 고유 기능
├─ 보험료 조회
├─ 가입 심사
└─ 계약 상태 조회
```

그러나 예약어 치환, 지연 콜백, 사용자 설정 조회, 실제 서버 Relay는 같다.
따라서 보험 고유 코드만 새 모듈에 작성한다.

```text
mock-server-insurance
├── 보험사별 가입 요청 Handler
├── 가입 심사 응답 시나리오
└── 보험 계약 상태 콜백 처리

mock-server-insurance-admin
└── 보험 테스트 설정 관리
```

보험 서비스는 공통 모듈의 예약과 JSON 치환 기능을 그대로 사용한다. 별도
DB가 필요하면 보험 전용 DataSource 설정만 추가한다.

### 별도 DataSource가 필요한 이유

신용대출 설정은 대출 DB에, 보험 설정은 보험 DB에 저장될 수 있다.

```text
mock-server-loan      → loan_mock_db
mock-server-insurance → insurance_mock_db
```

각 서비스 모듈은 자신의 Repository와 DataSource 설정을 가진다. 공통 모듈은
어느 DB를 사용하는지 몰라도 된다.

설정 파일도 서비스별로 나누면 보험 DB 주소를 변경할 때 신용대출 설정까지
건드리지 않아도 된다.

```text
application-loan.properties
application-insurance.properties
```

7번의 핵심은 하나의 거대한 범용 Handler를 만드는 것이 아니다. 콜백, 치환,
Relay 같은 공통 실행 구조만 재사용하고, 대출이나 보험의 업무 규칙은 별도
모듈에 두는 것이다.

## 핵심 설계 원칙

### 테스트 제어를 기존 업무 로직 밖에 둔다

헤더 주입과 Relay를 이용하면 운영 코드에 테스트 분기를 섞지 않아도 된다.
테스트 편의 때문에 실제 서비스의 복잡도가 증가하는 일을 피한다.

### 응답 값보다 상호작용을 재현한다

좋은 Mock 환경은 JSON 하나를 반환하는 데 그치지 않는다. 동기 응답, 지연
콜백, 실제 서버 전달, 제휴사 콜백 수신 등 프로토콜의 흐름 전체를 재현한다.

### 테스트 데이터를 실제 내부 데이터와 연결한다

템플릿 치환을 통해 원장 데이터와 정합성을 맞춰야 후속 단계까지 의미 있는
통합 테스트가 가능하다.

### 셀프서비스 도구까지 제품으로 본다

DB를 직접 수정하게 두지 않고 메신저봇으로 상태 조회와 변경을 제공했다.
테스트 인프라도 사용성과 가시성이 있어야 팀 전체의 생산성을 높인다.

## 적용할 때 추가로 확인할 점

아래 항목은 원문 구현을 다른 시스템에 적용할 때 함께 검토할 사항이다.

- 예약 작업의 중복 실행 방지뿐 아니라 실패 재시도와 최종 실패 처리도
  정의해야 한다.
- 주기 조회 간격에 따라 짧은 콜백 지연의 정확도가 달라질 수 있다.
- 템플릿 예약어의 타입을 모두 문자열로 치환하면 숫자와 불리언 타입이
  달라질 수 있으므로 스키마 검증이 필요하다.
- 테스트용 헤더를 외부 사용자가 위조하지 못하도록 환경 격리와 인증이
  필요하다.
- Relay 서버가 단일 장애점이 되지 않도록 타임아웃, 서킷 브레이커,
  관측성을 준비해야 한다.
- 사용자별 설정은 테스트 종료 후 자동 만료하거나 초기화할 방법이 필요하다.

## 정리

이 사례의 핵심은 Mock 서버를 단순한 가짜 API가 아니라 **외부 연동을
통제하는 테스트 플랫폼**으로 설계한 것이다.

- 커스텀 헤더로 테스트 문맥을 전달한다.
- DB 설정으로 사용자·제휴사·퍼널별 시나리오를 제어한다.
- 스케줄러와 분산 잠금으로 비동기 콜백을 재현한다.
- 템플릿 치환으로 실제 원장과 맞는 응답을 만든다.
- Relay로 Mock과 실제 제휴사를 같은 경로에서 선택한다.
- 메신저봇과 모듈화로 사용성과 확장성을 확보한다.

외부 기관에 의존하는 서비스에서는 테스트 대상을 흉내 내는 것만큼, 실제
연동과 Mock 사이를 안전하고 쉽게 전환하는 제어면을 만드는 것이 중요하다.
