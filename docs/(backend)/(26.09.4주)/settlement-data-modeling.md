# 정산 시스템의 데이터 모델링 개선

기존 정산 시스템은 거래별 계산 결과를 각각 저장하지 않고, 특정 기준으로 미리 합산한 결과만 저장했다.

## 기존 구조: 합계만 저장한다

가맹점 A에서 다음 거래가 발생했다고 가정하자.


| 거래   | 결제 금액   | 수수료  | 지급액     |
| ---- | -------: | ----: | -------: |
| 거래 1 | 10,000원 | 300원 | 9,700원  |
| 거래 2 | 20,000원 | 600원 | 19,400원 |
| 거래 3 | 30,000원 | 900원 | 29,100원 |


기존 시스템은 위 결과를 거래별로 남기는 대신 다음과 같은 합계만 저장했다.


| 가맹점   | 정산일        | 결제 합계   | 수수료 합계 | 지급 합계   |
| ----- | ---------- | -------: | ------: | -------: |
| 가맹점 A | 2026-09-23 | 60,000원 | 1,800원 | 58,200원 |


가맹점에 지급할 금액만 확인할 때는 데이터가 적고 조회도 빠른 구조다. 하지만 오류를 추적하거나 다른 기준으로 데이터를 분석해야 할 때 한계가 생긴다.

## 문제 1: 잘못 계산된 거래를 찾을 수 없다

수수료 합계가 1,800원이어야 하는데 1,700원으로 저장됐다고 가정하자.

```text
예상 수수료: 1,800원
실제 수수료: 1,700원
차이: 100원
```

합계만으로는 다음 질문에 답하기 어렵다.

- 어느 거래의 계산이 잘못됐는가?
- 잘못된 수수료율이 적용됐는가?
- 일부 거래가 누락됐는가?
- 같은 거래가 중복 처리됐는가?

거래별 결과가 이미 사라졌으므로 차이가 발생한 지점을 역추적할 수 없다.

## 문제 2: 다른 기준으로 다시 집계할 수 없다

데이터를 `가맹점 + 정산일` 기준으로 합친 뒤 다음과 같은 요구사항이 추가될 수 있다.

- 결제수단별 수수료 조회
- 상품별 매출 조회
- 해외 결제만 별도 집계
- 체크카드 거래만 조회
- 특정 수수료율이 적용된 거래 검색

```text
거래 1 + 거래 2 + 거래 3
             ↓ 합산
        지급액 58,200원
             ↓
      개별 거래로 복원 불가
```

작은 단위 데이터로 합계를 만드는 것은 가능하지만, 합계만으로 원래의 개별 데이터를 복원하는 것은 불가능하다.

## 개선 1: 거래 단위로 저장한다

신규 시스템은 결제 거래 한 건과 정산 결과 한 건이 대응하도록 변경했다.

```text
결제 거래 1건 ↔ 정산 결과 1건
```


| 거래 ID | 가맹점 | 결제수단 | 결제 금액   | 수수료  | 지급액     | 상태  |
| ----- | --- | ---- | -------: | ----: | -------: | --- |
| T-001 | A   | 신용카드 | 10,000원 | 300원 | 9,700원  | 성공  |
| T-002 | A   | 체크카드 | 20,000원 | 600원 | 19,400원 | 성공  |
| T-003 | A   | 해외카드 | 30,000원 | 900원 | 29,100원 | 성공  |


이제 오류가 발생하면 개별 거래를 비교할 수 있고, 동일한 원본으로 여러 형태의 집계를 만들 수도 있다.

```sql
-- 결제수단별 수수료 집계
SELECT payment_method, SUM(fee)
FROM settlement_result
GROUP BY payment_method;
```

```text
거래 단위 정산 결과
├── 가맹점별 집계
├── 결제수단별 집계
├── 날짜별 집계
├── 상품별 집계
└── 장애 거래 추적
```

다만 상세 데이터를 보존하면 저장량과 실시간 집계 비용이 증가한다. 이 문제는 이후 파티셔닝, 인덱스와 조회 전용 테이블로 보완한다.

## 개선 2: 계산 당시의 설정을 스냅샷으로 저장한다

거래별 결과만 저장해도 해당 결과가 왜 나왔는지 설명하지 못하는 경우가 있다.

```text
거래 금액: 100,000원
저장된 수수료: 3,000원
현재 계약의 수수료율: 2%
```

현재 계약만 보면 수수료가 2,000원이어야 하는 것처럼 보인다. 하지만 계산 당시에는 수수료율이 3%였고, 이후 계약이 2%로 변경됐을 수 있다.

```text
9월 1일 계산 당시: 수수료율 3%
9월 10일 계약 변경: 수수료율 2%
```

이를 해결하기 위해 결과와 함께 계산 당시 사용한 계약 조건을 스냅샷으로 저장한다.

```json
{
  "transactionId": "T-001",
  "amount": 100000,
  "fee": 3000,
  "contractSnapshot": {
    "feeRate": 0.03,
    "fixedFee": 0,
    "vatIncluded": true,
    "contractVersion": 7
  }
}
```

이제 시간이 지난 뒤에도 다음과 같이 계산 결과를 설명할 수 있다.

```text
이 거래는 계산 당시 수수료율 3%와
VAT 포함 계약을 적용했기 때문에
수수료가 3,000원으로 계산됐다.
```

즉, 최종 결과뿐만 아니라 **그 결과가 만들어진 당시의 맥락**까지 보존하는 것이다.

## 개선 3: 거래마다 처리 상태를 저장한다

기존 시스템은 수천만 건의 거래를 하나의 트랜잭션으로 처리하고, 모든 계산이 끝난 뒤 한 번에 커밋했다.

```text
거래 1 처리
거래 2 처리
...
거래 9,999,999 처리
거래 10,000,000에서 실패
             ↓
       전체 트랜잭션 롤백
```

신규 시스템은 각 거래의 처리 상태를 독립적으로 기록한다.


| 거래 ID | 상태        | 실패 원인    |
| ----- | --------- | -------- |
| T-001 | `SUCCESS` |          |
| T-002 | `FAILED`  | 계약 정보 없음 |
| T-003 | `SUCCESS` |          |


따라서 실패한 거래만 골라 다시 처리할 수 있다.

```sql
SELECT *
FROM settlement_result
WHERE status = 'FAILED';
```

```text
기존 방식: 전체 1,000만 건 재처리
개선 방식: 실패한 거래만 재처리
```

이를 상태 기반 재처리라고 한다. 장애가 발생해도 이미 성공한 거래는 유지하고 실패한 부분만 복구하므로 복구 시간과 비용이 줄어든다.

## 데이터 한 건이 답할 수 있어야 하는 질문

개편된 정산 데이터는 다음 질문에 답할 수 있어야 한다.

```text
정산 결과
├── 어떤 거래인가?
├── 얼마로 계산됐는가?
├── 어떤 계약과 설정을 사용했는가?
├── 계산 당시 환율은 무엇인가?
├── 처리에 성공했는가?
└── 실패했다면 이유가 무엇인가?
```
