# 20년 된 결제 시스템을 중단 없이 현대화하기

## 출발점

초기 환경에는 다음과 같은 문제가 있었다.

- 실제 운영 코드와 저장소의 코드가 일치하지 않았다.
- 일부 소스코드는 개인 PC나 개발 서버에만 남아 있었다.
- 제조사 지원이 끝난 서버와 OS 때문에 보안 패치가 어려웠다.
- DNS 등록, 서버 설정, 라우팅 변경 등을 수작업으로 처리했다.
- 개발자와 서버마다 빌드 결과가 달랐다.
- 표준화된 배포 및 운영 절차가 없었다.

이 환경에서는 뛰어난 개발자를 채용하더라도 레거시의 제약을 벗어나기
어렵다. 따라서 단순히 오래된 기술을 교체하는 것이 아니라, 개발자가
안전하고 빠르게 성과를 낼 수 있는 환경을 만드는 것을 목표로 삼았다.

## 두 가지 작업을 병행한다

전체 시스템을 한 번에 교체하면 결제 서비스의 안정성을 보장하기 어렵다.
해당 기업은 신규 개발 기반과 기존 시스템 개선을 함께 진행했다.

```text
Track 1: AWS와 모던 스택으로 신규 제품을 빠르게 개발
Track 2: 서비스 중단 없이 기존 시스템을 단계적으로 개선
```

이 전략은 레거시 개선이 끝날 때까지 신규 사업을 미루지 않으면서도,
기존 가맹점과의 호환성을 유지하는 점진적 전환 방식이다.

## 1. 운영 중인 소스코드를 복구한다

가장 먼저 실제 서비스 코드가 무엇인지 확인해야 했다. 운영 서버의
`.class` 파일을 역어셈블하고 개인 PC, 개발 서버, SVN에 흩어진 소스와
비교해 최신 코드를 찾아냈다.

복구한 코드는 GitHub Enterprise로 옮겼다. 이후 커밋 해시를 기준으로
정확한 버전을 배포할 수 있게 되었고, 코드 리뷰와 협업도 가능해졌다.

이 단계의 핵심은 현대화보다 **현재 상태를 재현할 수 있게 만드는 것**이다.
기준이 되는 코드가 없으면 이후의 빌드, 테스트, 배포 자동화도 신뢰할 수
없다.

## 2. 빌드를 재현 가능하게 만든다

기존에는 같은 Java 소스라도 개발자 PC와 운영 서버에서 서로 다른 결과가
나왔다. Gradle로 빌드 방식을 통합하고 Docker로 환경을 고정했으며,
의존성 버전도 명시했다.

그 결과 어느 환경에서나 같은 산출물을 만들 수 있게 되었다. 개발망에서
검증한 바이너리를 그대로 운영망에 배포할 수 있어 CI/CD와 자동 테스트의
기반도 마련됐다.

```text
소스코드 + 고정된 의존성 + 동일한 빌드 환경
                         ↓
                재현 가능한 산출물
```

## 3. MSA와 Kubernetes를 도입한다

결제 시스템은 결제창과 관리 서버만으로 구성되지 않는다. 다양한 결제수단,
가맹점 관리, 정산, 조회 등 복잡한 업무를 처리하기 위해 내부 서비스가
150개 이상으로 늘어났다.

각 서비스를 독립적으로 개발하고 배포할 수 있도록 MSA로 전환하고,
많은 서비스를 표준화된 방식으로 운영하기 위해 Kubernetes를 도입했다.

MSA(Microservices Architecture)는 하나의 큰 애플리케이션을 업무 단위의
작은 서비스로 나누는 설계 방식이다. 모든 기능을 함께 빌드하고 배포하는
모놀리식 구조와 달리 각 서비스가 독립적으로 실행되고, API나 메시지로
서로 통신한다.

**예시:** 하나의 애플리케이션이 결제부터 정산까지 모두 처리하던 구조를
다음과 같이 나눌 수 있다.

```text
고객의 결제 요청
       ↓
결제 서비스 ── 승인 요청 ──→ 카드 연동 서비스
       │
       ├── 결제 완료 이벤트 ──→ 정산 서비스
       └── 결제 완료 이벤트 ──→ 알림 서비스
```

카드 연동 기능을 수정할 때 카드 연동 서비스만 배포할 수 있고, 결제 요청이
급증하면 결제 서비스만 확장할 수 있다. 한 서비스의 장애가 다른 서비스로
확산되지 않도록 격리하는 것도 가능하다.

반면 서비스 수가 늘어나면 배포, 네트워크 연결, 장애 복구, 모니터링이
복잡해진다. Kubernetes는 여러 서비스의 실행 상태를 확인하고, 장애가 난
인스턴스를 다시 실행하며, 트래픽과 확장을 일관된 방식으로 관리하는 역할을
한다.

## 4. 고가용성 인프라를 구축한다

결제 서비스는 정기 점검이나 단일 인프라 장애로 장시간 중단될 수 없다.
동일한 형태의 Kubernetes 클러스터 4개를 AWS 가용영역과 IDC의 서로 다른
장애 격리 영역에 분산 배치했다.

개발자는 인프라 구조를 직접 다루는 대신 추상화된 CI/CD 플랫폼으로 배포와
모니터링을 수행한다. 애플리케이션뿐 아니라 VM과 클러스터 계층에서도
트래픽을 1% 단위로 조절해 카나리 배포할 수 있다.

```text
신규 버전 또는 클러스터
  1% → 관찰 → 점진적 확대 → 전체 전환
                    └─ 이상 발생 시 트래픽 제거
```

**예시:** 한 가용영역의 네트워크에 장애가 발생하면 해당 클러스터로 향하던
결제 트래픽을 정상 클러스터로 보낸다. 신규 버전을 배포할 때도 먼저 전체
요청의 1%만 전달하고, 결제 성공률과 응답 시간을 확인한 뒤 10%, 50%,
100%로 늘린다. 오류가 증가하면 즉시 신규 버전의 트래픽을 제거한다.

## 5. 공통 변경을 자동화한다

서비스 수가 많아지면 보안 패치나 공통 라이브러리 업데이트를 각 팀에
요청하는 방식으로는 일관성을 유지하기 어렵다.

로깅과 모니터링 같은 공통 기능은 애플리케이션 코드를 침범하지 않고
런타임에 주입되도록 만들었다. 문제가 있는 코드 패턴이나 라이브러리가
발견되면 코드를 자동으로 수정하고 Pull Request를 생성하는 시스템도
구축했다.

이를 통해 전사 공통 변경을 빠르게 배포하고, 다수의 JVM 서비스를
Java 17 또는 21로 전환할 수 있었다.

**예시:** 150개 서비스가 같은 로깅 라이브러리의 취약한 버전을 사용한다고
가정하자. 담당 팀마다 업데이트를 요청하면 일부 서비스가 누락될 수 있다.
자동화 시스템은 다음 작업을 서비스마다 반복한다.

```text
1. 저장소에서 의존성 설정 파일을 찾는다.
2. 로깅 라이브러리 버전을 1.0에서 1.1로 변경한다.
3. 테스트를 실행해 기존 기능이 정상인지 확인한다.
4. 변경 내용과 테스트 결과를 PR(Pull Request)로 제출한다.
5. 담당자가 검토하고 승인하면 기본 브랜치에 반영한다.
```

PR은 변경 사항을 바로 운영에 적용하는 것이 아니라, 저장소에 반영하기 전
담당자에게 검토와 승인을 요청하는 절차다. 자동화 시스템은 반복적인 수정과
테스트를 대신하지만, 최종 반영 여부는 서비스 담당자가 결정한다.

## 6. 성능과 안정성을 함께 개선한다

안정적인 점진 배포 외에도 사용자와 외부 금융사 사이의 통신 성능을
개선했다.

- 모바일 네트워크의 지연과 패킷 손실에 대응하기 위해 HTTP/3과
TLS 1.3을 적용했다.
- 순간적인 트래픽 폭증과 캐시 장애에 대비해 다계층 캐시를 구성했다.
- 카드사와 유지하는 소수의 TCP 연결을 비동기로 사용하는 멀티플렉싱
서버를 개발했다.

그 결과 결제 요청이 몰릴 때 일부 거래의 응답이 늦어지거나 실패하던
문제를 줄였다.

**예시:** 한정 상품 판매가 시작되면서 평소보다 수십 배 많은 결제 요청이
동시에 들어올 수 있다. 자주 조회하는 가맹점 설정과 카드사 정보를 여러
캐시 계층에서 제공하면 원본 DB로 요청이 한꺼번에 몰리는 것을 막을 수
있다. 카드사 통신은 연결을 요청마다 새로 만들지 않고, 유지 중인 TCP
연결에서 여러 요청을 비동기로 처리해 대기 시간을 줄인다.

## 7. 수십억 건의 데이터를 실시간 조회한다

가맹점은 세금 신고와 회계 처리를 위해 월·분기·연 단위 거래 데이터를
조회한다. 하지만 결제 데이터에는 다음과 같은 특성이 있다.

- 수십억 건이 여러 서비스의 DB에 분산되어 있다.
- 몇 년 전 결제도 취소될 수 있어 과거 데이터가 불변하지 않다.
- 거래와 통계가 수십 초 안에 조회 결과에 반영되어야 한다.
- 긴 기간에 대한 집계와 복합 조건 검색이 필요하다.

이를 처리하는 대규모 조회 플랫폼을 구축한 결과, 약 1분 걸리던 쿼리를
1초 이내로 줄였다. 조회 범위도 최근 3개월에서 최대 보관 기간인 5년으로
확대했다.

**예시:** 가맹점이 작년 연간 매출을 조회한 직후, 2년 전에 발생한 결제의
부분 취소가 접수될 수 있다. 미리 만든 통계만 보여주면 취소 금액이 빠진
잘못된 매출이 표시된다. 거래 변경을 수십 초 안에 조회 플랫폼에 반영하면
과거 거래가 바뀌어도 최신 연간 합계를 1초 이내에 제공할 수 있다.

## 8. 보안을 기본값으로 만든다

모든 서비스를 VM 또는 컨테이너 기반으로 재구성해 Golden Image를 통한
주기적인 자동 패치가 가능하게 했다. 네트워크 경계뿐 아니라 내부망,
업무망, 호스트와 컨테이너 런타임까지 보안 범위를 확장했다.

모든 엔드포인트는 TLS 1.3을 지원하며, 민감한 API에는 애플리케이션
계층의 추가 암호화를 적용했다. ZTNA와 AI 기반 보안 이벤트 분석도
도입했다.

**예시:** OS 보안 취약점이 발견되면 운영자가 서버 수백 대에 접속해
패치하는 대신, 패치가 적용된 Golden Image를 만든다. 검증을 마친 새
이미지로 VM과 컨테이너를 순차 교체하면 모든 서비스에 같은 보안 기준을
적용하고 누락 여부도 추적할 수 있다.

## 9. 애플리케이션을 전면 개편한다

마지막 단계에서는 2000년대 초반 구조의 애플리케이션을 현대적인
아키텍처로 전환했다.


| 영역     | 기존                 | 개선                         |
| ------ | ------------------ | -------------------------- |
| 프론트엔드  | JSP, jQuery        | React, TypeScript, 디자인 시스템 |
| 백엔드    | Struts 1.2, iBATIS | Kotlin, Spring Boot 3      |
| 데이터베이스 | 단일 Oracle DB       | 서비스별로 격리된 DB               |
| 배치     | 수천 줄의 SQL          | 코드 기반 비즈니스 로직              |
| 인프라    | 온프레미스 물리 서버        | VM, 컨테이너, 하이브리드 클라우드       |
| 배포     | 수동 배포              | IDC와 AWS를 추상화한 CI/CD       |
| 보안     | 수작업 점검             | Security by Default        |


기존 수만 개 가맹점의 연동 방식은 임의로 변경할 수 없었다. 새 시스템이
20년 동안 제공한 기능과 동작을 그대로 지원하는지 45만 개 규모의 자동
회귀 테스트로 확인하면서 전환했다.

**예시:** 기존 가맹점이 `CARD`, `10000`, `3`이라는 문자열로 카드 결제와
금액, 할부 개월을 전달한다면 새 시스템도 이 요청을 그대로 받아야 한다.
외부 요청은 호환 계층에서 새로운 결제 모델로 변환하고, 기존 시스템과 새
시스템에 같은 요청을 실행해 승인 결과와 오류 응답이 같은지 자동으로
비교한다. 가맹점은 연동 코드를 바꾸지 않아도 내부 시스템만 교체된다.

## 결과

현재는 Public Cloud와 Private Cloud가 결합된 환경에서 물리적
인프라를 추상화해 제공한다. 개발팀은 표준화된 플랫폼을 통해 동일한
방식으로 서비스를 개발하고, 배포하고, 관찰할 수 있다.

주요 결과는 다음과 같다.

- 커밋부터 운영 환경까지 추적 가능한 배포 체계를 갖췄다.
- 인프라와 애플리케이션 전 계층에서 점진 배포가 가능해졌다.
- 표준화와 자동화로 150개 이상의 서비스를 일관되게 운영한다.
- 수십억 건의 거래 데이터를 1초 이내에 조회할 수 있게 됐다.
- 기존 가맹점의 연동을 유지하면서 애플리케이션을 현대화했다.

## 핵심 교훈

### 먼저 재현 가능성을 확보한다

레거시 현대화의 첫 단계는 최신 프레임워크 도입이 아니다. 운영 코드,
빌드 결과, 배포 버전을 정확히 재현할 수 있어야 이후의 변경을 신뢰할 수
있다.

### 신규 개발과 레거시 개선을 병행한다

레거시를 모두 제거한 뒤 신규 사업을 시작하면 시장 변화에 대응하기
어렵다. 새로운 제품을 위한 기반을 마련하는 동시에 기존 시스템을
점진적으로 개선해야 한다.

### 복잡성을 플랫폼에서 흡수한다

고가용성, 배포, 모니터링, 보안 같은 공통 문제를 각 개발팀이 반복해서
해결하게 하지 않는다. 플랫폼이 인프라 차이를 추상화하고 안전한 기본값을
제공하면 개발자는 비즈니스 문제에 집중할 수 있다.

### 레거시의 계약을 존중한다

오래된 시스템은 제거해야 할 코드만을 의미하지 않는다. 수많은 고객과
연결된 인터페이스이자 오랜 기간 축적된 비즈니스 규칙이기도 하다.
현대화 과정에서는 기존 계약을 테스트로 보존하면서 내부 구현을 단계적으로
교체해야 한다.
