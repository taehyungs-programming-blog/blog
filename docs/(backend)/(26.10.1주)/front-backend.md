# 프론트엔드와 백엔드를 한 팀으로 합치면 어떤 일이 일어날까?

## 1. 한 줄 요약

FE 4명 + BE 4명을 한 팀으로 합친 첫 분기 동안 완료량은 줄지 않았다.

AI 코딩 도구와 팀에 쌓인 문서가 진입 장벽을 낮췄다.

전문성은 "생산자"에서 "AI 결과물을 거르는 검증자"로 옮겨가고 있다.

## 2. 배경

2026년 9월 28일 오전 10:26

| 항목 | 내용 |
| --- | --- |
| 팀 역할 | 광고 생성·운영·결과 리포트까지 광고주 여정 전체 담당 |
| 통합 전 구조 | FE 팀, BE 팀이 분리 |
| 인원 | BE 4명 + FE 4명 = 8명 |
| 기술 스택 | BE: JVM 계열 / FE: 주로 React |
| 시스템 | 마이크로서비스, 팀별로 여러 서비스 운영 |

### 통합 전 문제

- 기능 하나에 FE/BE 티켓이 따로 생성됨
- 두 팀의 스프린트 일정을 서로 맞춰야 함
- API 스펙 확정 전까지 FE 작업 대기
- 한쪽이 밀리면 반대쪽도 같이 밀림
- 각자 잘해도 직군 경계에서 조율·대기 비용 발생

### 통합 전 걱정

1. **안정성**: 8명이 함께 온콜 → 낯선 서비스 장애에 대응 못 할 가능성
2. **속도**: 낯선 영역 학습으로 팀 전체가 느려질 가능성

## 3. 결과: 속도

- 기준선: 통합 전 BE 팀(4명)의 스프린트 완료량 기록
- 인원 2배만큼 기대치 상향, 신규 합류분은 보수적으로 계산
- 2주 스프린트 × 4회 동안 완료량이 큰 변동 없이 유지
- 측정 단위: 스토리 포인트 (절대값이 아닌 추세로 판단)
- 2분기 특성: 운영성 업무가 완료량의 1/3, 인시던트 대응 다수

## 4. 지킨 두 가지 원칙

별도의 거창한 온보딩 프로그램은 없었다.

### 4.1 배분

- 전원이 스프린트마다 **최소 1개 반대 직군 티켓** 담당
  - 과제가 원래 FE/BE 세트로 움직여서 억지로 만들 필요 없음
- 크기는 소화 가능한 것부터
- FE 온콜에서 나온 간단한 운영·유지보수 티켓, 간단한 BE 티켓
- BE → 자기 작업에서 파생되는 FE 개발

### 4.2 시범

- 팀 리드(BE 엔지니어)가 FE 작업을 먼저 수행
- 간단한 티켓부터 규모 있는 마이그레이션까지 직접 진행
- 과정에서 만든 검증 도구는 팀 재사용용으로 남김
- 반대 직군 작업에 대한 막연한 두려움·거부감을 낮춤

## 5. 원칙이 통한 이유: 기본기

### 이미 있던 것 (1분기)

- 팀 매니페스토, Working Agreements (일하는 방식 합의 문서)
- 2주 스프린트 습관: 모든 일이 티켓화 → 크기 추정 + 분배
- 덕분에 반대 직군 일을 "적정한 크기"로 배분 가능
- 작업마다 기획서·설계 문서 작성 습관
- 서비스 저장소별 아키텍처 다이어그램, DB 스키마 문서
- 온콜 Runbook(증상별 대응 절차), 모니터링 대시보드

### 새로 만든 것 (2분기)

- 팀 기술 문서 저장소: 흩어진 도메인 지식 통합
- 한 분기 동안 문서·수정 기록 수백 개 누적
- 만든 문서가 곧바로 다음 작업·포스트모템의 AI 입력으로 사용
- 비동기 스터디: 챕터별 인터랙티브 자료로 학습
- 결과물이 다시 AI의 입력으로 순환
- 문서 노후화 대응: 기획서·테크스펙 리뷰 단계마다 보정

### AI + 문서

- AI 코딩 도구가 반대 직군 코드 초안의 대부분을 작성
- 언어·기술 스택 차이는 더 이상 큰 걸림돌이 아님
- AI가 낯선 코드베이스에서 쓸 만한 결과를 내려면 맥락이 필요
- 그 맥락 = 팀 문서: **"팀의 지식이 AI의 연료"**
- 지식 구축과 활용을 순서대로가 아니라 동시에 해도 효과가 누적됨

## 6. 일하는 방식의 변화

### 경계를 넘는 작업이 일상화

- 예: BE 엔지니어가 "[FE] 대행사 계정 예산 연동" 완료
- 예: FE 엔지니어가 "[BE] 세금계산서 정보 타입 전환 API" 완료
- 직군 간 티켓 대기·조율 비용 크게 감소

### 검증 방식

- "혼자 끝까지" ≠ "혼자 다 안다"
- 무엇이 불확실한지 아는 것 자체가 전문성
- 전문성 = AI를 넘는 장벽이 아니라 **최종 검증자**

## 7. 비용과 한계

### 1인 풀스택 리스크 (과제로 인지 중)

- 직군 관점 리뷰가 옅어질 수 있음
- 특정 영역 지식이 한 사람에게 쏠릴 수 있음
- 장기적으로 전문성이 얕아질 수 있음
- 대응: 상호 검증, 스터디 → 아직 "관리"보다 "인지" 단계

### 이미 치른 비용

- **예측가능성 저하**: 실제로 한 일의 2/3가 계획에 없던 일
  - AI로 병렬 진행 → 발견된 일·급한 요청이 바로 스프린트에 추가
  - 계획한 티켓은 대체로 완료했지만 총량의 내용이 계획과 다름
- **추정 감각 불일치**: 처리 시간은 줄었는데 추정은 예전 속도 기준
  - 일을 크게 잡는다는 가설을 회고에서 검증 중
- **팀 감각 약화**: 각자 병렬로 일해서 서로 하는 일을 잘 모름
- 기타
  - 스프린트 중간 회의·추가 업무 야근 발생
  - 온콜 시 CS 처리 부담이 예상보다 큼
  - AI 도구의 팀 표준 습관화는 진행 중

### 다음 분기 과제

- 방식의 지속가능성 확보, 특히 예측가능성 회복

## 8. 핵심 결론

1. AI가 직군 간 진입장벽을 실제로 낮췄다.
2. 전문성은 "생산자"에서 "AI 결과물을 거르는 검증자"로 옮겨가고 있다.
3. AI의 연료는 팀이 쌓아둔 문서였다.
