# LINE 통화 영상 재생 품질 개선 사례

## 1. 배경

### 1.1 왜 통화는 네트워크 적응이 더 어려운가

| 구분 | 라이브 스트리밍 | LINE 통화 |
| --- | --- | --- |
| 방향 | 단방향 | 양방향 실시간 |
| 허용 지연 | 수 초도 가능 (버퍼링으로 흡수) | 1초만 늦어도 대화가 어색 |
| 손실 대응 | 버퍼를 크게 두고 재전송 가능 | 버퍼를 크게 둘 수 없음 |

- 그래서 네트워크 상태에 맞춰 전송량(비트레이트)을 실시간으로 조절하는 네트워크 적응 기술이 통화 품질을 좌우한다.

### 1.2 발견된 이상 패턴

일본의 통화 지표에서 월 단위로 반복되는 패턴이 관찰되었다.

2026년 9월 30일 오후 12:45

```text
월초: FPS 높음 → 월말: FPS 감소 → 다음 달 1일: FPS 회복
```

- 월초: 영상 디코딩 FPS 높음 (부드러움)
- 월말로 갈수록: FPS 점진적 감소 (끊김 증가)
- 다음 달 1일: 다시 회복

태국 등 다른 국가에서는 이런 패턴이 없었다.

예시: 사용자가 월초에는 30fps로 영상을 보다가, 월말에는 같은
네트워크 품질(신호 세기)인데도 10fps 안팎으로 뚝뚝 끊겨 보이는 상황.

## 2. 원인 분석

### 2.1 단서 1: FPS 변화 = 패킷 손실률 변화

- 월간 FPS 곡선은 비디오 미디어 패킷 손실률 곡선과 정확히 반대로 움직였다. (손실률 증가 → FPS 하락)

### 2.2 단서 2: 네트워크 유형과 통화 종류별 분해

| 조건 | 월말 악화 |
| --- | --- |
| Wi-Fi ↔ Wi-Fi | 없음 |
| 모바일(4G) ↔ 모바일 | 뚜렷함 |
| 영상 통화 | 음성 통화보다 훨씬 심함 |

- Wi-Fi에서는 없고 모바일에서만 나타난다.
- 영상이 음성보다 심하다.
- 사용자 기기나 앱 문제가 아니라 이동통신 요금제의 특성이 의심됨

> 전송량이 큰 트래픽일수록 제한에 걸리기 쉬움 (참고: 음성은 수십 Kbps, 영상은 수백 Kbps ~ 수 Mbps 수준)

### 2.3 근본 원인: 데이터 소진 후 속도 제한

- 월 기본 데이터를 다 쓴 사용자에게 속도(비트레이트) 제한이 걸린다.
- 결론
  - 월초: 제한 없음 → HD 영상 전송 가능
  - 월말: 데이터 소진 → 제한된 대역폭 안에서 통화해야 함
  - 다음 달 1일: 데이터 할당량 초기화 → 복구

## 3. 문제의 핵심: 지연 없이 손실만 생기는 환경

### 3.1 기존 혼잡 제어: CCFS

- CCFS = Congestion Control based on Forward path Status
- LINE 통화가 IETF 표준(NADA, SCReAM) 대신 사용하는 자체 개발 송신자 기반(sender-based) 혼잡 제어기
- 동작

1. 수신자가 주기적으로 피드백을 보낸다.
   (각 패킷의 수신 시각, 수신 여부)
2. 송신자가 피드백으로 전송 경로(forward path)의 상태를 판단한다.
3. 상태에 따라 비트레이트를 조정한다.

| 상태 | 의미 |
| --- | --- |
| Default | 정상 |
| Probing | 더 보낼 수 있는지 대역폭 탐색 |
| Throttled | 혼잡 감지, 비트레이트 낮춤 |
| Competing | 다른 트래픽과 경쟁 중 |

- 혼잡 판정 기준 (지연 기반)
  - 패킷 지연이 연속으로 증가하고
  - 지연 변화값이 임계치를 넘으면 Throttled

예시: 교차로 대기열처럼, 병목 구간에 패킷이 쌓이기 시작하면
도착 지연이 20ms → 35ms → 60ms → 110ms로 계속 커진다. CCFS는
이 상승 추세를 보고 "혼잡"으로 판단해 비트레이트를 낮춘다.

### 3.2 왜 기존 방식이 놓쳤나: 트래픽 폴리싱

- 혼잡이 생기는 방식은 크게 두 가지다.

| 방식 | 초과 트래픽 처리 | 지연 | 손실 |
| --- | --- | --- | --- |
| 큐잉 / 쉐이핑 | 큐에 쌓아 두었다가 천천히 내보냄 | 증가 | 큐가 넘치면 발생 |
| 폴리싱 (policing) | 한도를 넘는 패킷을 즉시 폐기 | 증가 없음 | 즉시 발생 |

- 데이터 소진 후 속도 제한 환경은 폴리싱에 해당한다.
  - 큐에 쌓이지 않으므로 지연은 그대로인데 패킷만 사라진다.
- 지연 기반인 CCFS는 이 상황을 혼잡으로 인식하지 못한다.
  - 계속 한도 이상으로 보내고, 손실이 누적되고, FPS가 떨어진다.

예시: 한도가 500kbps인 폴리서에 800kbps로 보내면
초과분 300kbps가 폐기되어 손실률은 약 37.5% (300/800)다.
이때 지연은 평소와 같은 30ms 안팎이라 CCFS 눈에는 "정상"이다.

```text
[큐잉 환경]
  지연: 20 → 35 → 60 → 110ms
  CCFS가 감지: O

[폴리싱 환경]
  지연: 30 → 31 → 29 → 30ms
  손실: 0% → 15% → 30% → 37%
  CCFS가 감지: X
```

## 4. 해결: 손실 기반 혼잡 제어 추가

### 4.1 단순 접근의 함정: 비트레이트 고갈

- "손실이 나면 비트레이트를 낮춘다"는 규칙을 그대로 넣으면 문제가 생긴다.
- 손실에는 혼잡과 무관한 일시적 원인이 많다.
  (참고: Wi-Fi 간섭, 핸드오버, 순간적 전파 약화 등)
- 그때마다 비트레이트를 낮추면 필요 이상으로 화질이 떨어지고, 낮아진 상태에서 회복하지 못하는 비트레이트 고갈 (bitrate starvation)이 발생한다.
- 필요한 것: 이 손실이 전송량 때문에 생긴 것인지 구별하는 기준

### 4.2 아이디어: 비트레이트와 손실률의 상관관계

- 폴리싱에 걸린 상황이라면 비트레이트를 올릴수록 손실률도 같이 올라간다. 일시적 손실이면 비트레이트와 무관하게 튄다.
- 이 관계를 피어슨 상관계수(Pearson correlation coefficient)로 수치화한다.
- 범위: -1 ~ 1
- 1에 가까움: 비트레이트가 오를 때 손실률도 오른다 (강한 양의 상관)
- 0에 가까움: 둘 사이에 관계 없음

### 4.3 계산 예시

예시: 최근 윈도에서 수집한 (비트레이트, 손실률) 6개 샘플

**케이스 A: 한도에 걸린 경우 (폴리싱)**

| 비트레이트(Kbps) | 300 | 400 | 500 | 600 | 700 | 800 |
| --- | --- | --- | --- | --- | --- | --- |
| 손실률(%) | 0 | 0 | 1 | 3 | 6 | 10 |

- 500kbps를 넘기면서부터 손실이 늘고, 높일수록 더 커진다.
- 상관계수 r ≈ 0.94 → 강한 양의 상관 → 혼잡으로 판단
- Throttled로 전이, 비트레이트를 낮춘다.

**케이스 B: 일시적 손실 (혼잡과 무관)**

| 비트레이트(Kbps) | 300 | 400 | 500 | 600 | 700 | 800 |
| --- | --- | --- | --- | --- | --- | --- |
| 손실률(%) | 0 | 4 | 0 | 0 | 5 | 0 |

- 손실은 있으나 비트레이트와 관계없이 튄다.
- 상관계수 r ≈ 0.07 → 상관 없음 → 일시적 손실로 판단
- 비트레이트 유지, 화질 보존

### 4.4 개선된 제어 흐름

1. CCFS 피드백에서 비트레이트, 패킷 손실률을 실시간 수집
2. 일정 윈도 내에서 둘의 상관계수를 지속 갱신
3. 손실이 임계치 이상 발생하면 상관계수를 확인

   - 상관계수 ≥ 기준값: 혼잡으로 판단 → Throttled 전이
   - 상관계수 < 기준값: 일시적 손실로 판단 → 비트레이트 유지

4. 혼잡이 확인된 경우에만 비트레이트를 조정

- 지연 기반 감지는 그대로 두고 손실 기반 경로를 추가하는 구조다.
  (큐잉 환경은 기존 방식, 폴리싱 환경은 새 방식이 담당)

## 5. 배포 결과

### 5.1 지표 변화

| 지표 | 국가 | 변화 |
| --- | --- | --- |
| 비디오 패킷 손실 (월말) | 일본 | 약 22% 감소 |
| 비디오 디코딩 FPS | 일본 | 약 14% 상승 |
| 비디오 디코딩 FPS | 태국 | 약 5% 상승 |
| 비디오 전송 비트레이트 (월말) | 일본 | 약 1% 하락 |

예시: 수치 해석 (기준값은 임의). 월말 FPS가 20이었다면 14% 상승은
약 22.8fps, 손실률이 5%였다면 22% 감소는 약 3.9%에 해당한다.

### 5.2 해석

- 일본: 월말 악화가 크게 완화되었다.
- 태국: 월간 패턴이 없던 곳인데도 FPS가 올랐다.
- 월 단위 데이터 소진과 별개로 다른 형태의 비트레이트 제한 (예: 요금제별 속도 제한 등)이 존재한다고 해석한다.
- 부작용: 비트레이트가 약 1%만 내려갔다.
- 손실이 있는 환경에서만 Throttled로 전이했기 때문에 화질 영향이 미미하다.
- 핵심: 손실을 줄이면서 (속도를 조금만 낮추면서) 재생 FPS가 올랐다.

"많이 보내는 것"보다 "버려지지 않게 보내는 것"이 재생 품질에 유리하다는 것을 보여준다.
