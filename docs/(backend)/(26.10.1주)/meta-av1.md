# Meta의 RTC AV1 도입 정리

2026년 9월 29일 오후 12:50

## 1. 배경 / 도입 이유

- Meta 설정 기준 H.264/AVC 대비 비트레이트 **최소 20% 절감**
- RTC 네트워크 대역은 10 kbps ~ 400 kbps이며, 100 kbps 이하에서 화질 유지가 특히 어려움

### 1.1 문제와 AV1 도입 효과

기존 H.264 는 저대역에서 다음 문제가 있었고, AV1 으로 개선함.

| 문제 (H.264) | AV1 도입 효과 |
| --- | --- |
| 프레임당 비트가 적어(15fps 기준 약 800 byte) 양자화를 강하게 걸어야 하고, 그 결과 블록 노이즈·디테일 손실 발생 | 압축 효율이 높아 같은 비트레이트에서 더 나은 화질. H.264 대비 비트레이트 20% 이상 절감 |
| 움직임이 크면 잔차가 늘어 화질이 급격히 저하 | 예측 도구가 정교해 잔차가 줄어 화질 저하 완화 |
| 화면 공유에서 글자·UI 경계가 번지고 비트가 많이 듦 | palette mode, intra-block copy로 같은 비트에 더 선명한 화면 공유 (1.2) |

- 위 세 가지가 AV1 이 직접 개선하는 부분이며, 키프레임 비용, 레이트 컨트롤, 패킷 손실은 AV1 과 별개로 5절의 방법으로 대응함

### 1.2 화면 콘텐츠 도구: palette mode, intra-block copy

화면 콘텐츠(문서, 슬라이드, 코드, UI)의 특징

- 사용하는 색이 적고, 경계가 선명하며, 같은 패턴이 반복됨
- 일반 영상용 도구(DCT 변환 + 양자화)는 이런 콘텐츠에서 효율이 떨어짐. 날카로운 경계 주변에 링잉이 생기고 비트도 많이 필요함

Palette mode

- 블록 안에서 쓰는 색을 몇 개만 뽑아 팔레트로 구성하고, 각 픽셀은 색 값 대신 팔레트 인덱스만 저장
- 색 수가 적은 블록은 변환 없이 적은 비트로 표현되고 경계가 뭉개지지 않음
- 예: 흰 배경에 검은 글자 블록은 색 2개 + 픽셀별 0/1 값

Intra-block copy (IntraBC)

- 같은 프레임 안에서 이미 인코딩된 영역을 참조해 블록을 복사하고 블록 벡터(복사 위치)만 저장
- 글자, 아이콘, 창 요소가 반복될 때 효과가 큼
- 시간축 움직임 보상(inter prediction)과 비슷한 역할을 한 프레임
  안에서 수행

RTC 에서의 의미

- 화면 공유는 저대역에서도 글자가 읽혀야 하므로, 같은 비트로 더 선명한 결과를 내는 데 유리

## 2. 기술 접근

### 2.1 인코더/디코더

- 내부 저복잡도 AV1 인코더 통합
- 오픈소스 구현은 전력 사용이 14% 증가 → 커스텀 인코더로 H.264 수준으로 맞춤
- 디코더는 A/B 테스트 후 **dav1d** 선택 (효율·안정성)
- A/B 테스트: 사용자를 무작위로 두 그룹으로 나눠 각각 다른 버전을 쓰게 하고 지표를 비교하는 실험 방법. 실제 사용자의 기기·네트워크 환경에서 측정할 수 있음
- H.264/AVC 수준 복잡도의 초저복잡도 인코더 프리셋 개발
- 하드웨어 AV1 코덱에 의존하지 않고 소프트웨어로 처리하는 구조.
  하드웨어 미지원 기기도 소프트웨어 처리 또는 H.264 폴백으로 대응

### 2.2 기기 적합성 판단

- 실사용 성능 지표 기반 ML 프레임워크가 측정값을 입력으로 받아 기기의 AV1 성능을 나타내는 `rtc_score` 산출
- Model V1.1 (2025-08): 적용 범위 확대
- Model V2: 고사양/저사양 2단계 구분
- 지표 종류, 점수 기준값은 미공개
- 입력 특징: 기기 모델, SoC, 코어 수·클럭, 해상도별 인코딩·디코딩 시간, 프레임 드롭, 발열 상태 등의 실측 통계

### 2.3 복잡도 적응과 코덱 전환: "감당하지 못하면"의 기준

| 단계 | 조건 | 동작 |
| --- | --- | --- |
| 1 | 인코딩 지연이 실시간 한계에 근접 | 인코더 프리셋 하향 |
| 2 | 프리셋을 낮춰도 인코딩 지연이 안 내려옴 | H.264 전환 |
| 3 | 송신 측이 상대의 AV1 실시간 디코딩 불가를 감지 | H.264 전환 |
| 4 | 배터리 부족 | H.264 전환 |

- 각 기기는 통화 중 비디오 디코딩 지연을 계속 피드백
- 기기명만으로 판단하지 않고 런타임 지연 모니터링을 병행

공개되지 않은 부분

- 지연 임계값: 프레임당 인코딩 시간이 프레임 간격(15fps 면 약 66 ms)에 근접하거나 초과하는지를 기준으로 삼았을 가능성
- 순간값이 아닌 이동 평균, 일정 시간 지속 여부로 판단해 잦은 전환(플래핑)을 막았을 가능성
- 디코딩 지연 피드백: RTCP 확장이나 자체 RTP header extension 으로 주기적(수 초 단위) 전달했을 가능성
- 배터리 기준: 임계값 미공개. 통상 15~20% 이하 또는 절전 모드 진입 시로 잡는 경우가 많아 그 정도일 것
- 복귀 조건: 언급 없음. 조건이 회복되면 재시도하되 반복 전환을 막기 위해 대기 시간(hysteresis)을 뒀을 가능성

### 2.4 비대칭 코덱 (중급 기기)

- 중급 기기는 송신은 H.264, 수신은 AV1 로 방향별 코덱을 다르게 사용
- 일부 중급 기기는 실시간 AV1 인코딩은 못 하지만 디코딩은 가능
  - 디코딩은 인코딩보다 훨씬 가벼움
- 중급 기기는 받는 영상의 AV1 이득(같은 대역에서 더 나은 화질)만 얻고 인코딩 부담은 지지 않음
- 클라이언트가 기기 상태를 계속 모니터링해 적절한 코덱을 결정
- 중급·저사양 Android 로 AV1 지원을 확대해 적용 범위가 크게 증가

공개되지 않은 부분

- 협상: SDP offer/answer 에서 send 와 receive 코덱 능력을 분리해 광고하고 방향별로 코덱을 선택하는 구조일 가능성
- 통화 중 전환은 재협상 없이 payload type 교체, 또는 수신 측이 복수 코덱 디코딩을 준비해 두는 방식일 가능성
- 대상 기기: `rtc_score`로 인코딩 점수는 낮고 디코딩 점수는 충분한 기기를 중급으로 분류했을 가능성
- 효과: 수신 측만 AV1 이득을 얻으므로 상대가 고사양일수록 체감이 크고, 양쪽 모두 중급이면 H.264 로 동작할 가능성

## 3. 적용 범위

- Messenger, WhatsApp 등 모바일 기기 대다수에서 AV1 사용 중

## 4. 주요 과제와 수치, 그리고 모든 플랫폼에 쓰지 않는 이유

| 과제 | 내용 |
| --- | --- |
| 바이너리 크기 | 압축 기준 약 600 KB 증가. 주요 조직의 연간 바이너리 예산을 모두 소진. dynamic framework 라이브러리 최적화로 대응 |
| 전력 | 커스텀 저복잡도 인코더 개발 |
| 지연 민감도 | 멀티패스 버퍼링은 지연 증가, 비트레이트 급증은 프리즈 유발 |
| 패킷 손실 | 의존 체인이 길어 한 프레임 손실에도 복구 어려움 |
| 기기 성능 | 2023년 옥타코어 폰도 320×180@15fps 인코딩 감당 못 한 사례 |

- VBV 지연 목표: 200 ms 미만 (CBR 정확도)
- 그룹 통화는 다수 스트림 동시 디코딩 부담으로 아직 확대하지 못함
- 자체 인코더, ML 모델, 코덱 전환 로직, 레이트 컨트롤, LTR 등 개발 비용이 큼. Meta 규모라서 가능한 투자

### 4.1 H.264 하드웨어 코덱과 성능

- H.264 가 알고리즘상 더 빠른 것은 아님. 같은 화질 기준으로 AV1 이 연산량이 훨씬 큼
- H.264 의 이점은 거의 모든 기기에 전용 하드웨어 코덱이 있어 CPU
  부담과 전력이 거의 없다는 점

- AV1 은 전용 칩이 없는 기기가 많아 CPU 로 처리해야 함
- AV1 하드웨어 코덱이 있는 기기에서는 이 차이가 크게 줄어듦

### 4.2 그 외 도입을 제한하는 요인

- 호환성: 통화는 양쪽이 같은 코덱을 지원해야 하며 브라우저, SFU 서버, 연동 장비의 지원 편차가 있음
- 서버 측 처리: 트랜스코딩, 녹화 등 파이프라인 대응 필요
- 라이선스: AV1 은 로열티가 없어 H.264 와 달리 장점

## 5. 통화 품질 해법

### 레이트 컨트롤

- VBV 버퍼 추적으로 overshoot 방지
- 키프레임 비트레이트 엄격 제어
- overshoot 뿐 아니라 undershoot 도 방지

### 오류 복원력

- Temporal Layer (TL): enhancement 계층과 무관하게 base 계층 연속성 유지
- Long-Term Reference (LTR): 프레임 손실 후 빠른 재동기화
- 독자 RTP extension 으로 명시적 LTR 지시자 전달
- 사전(proactive)·사후(reactive) 복구 모두 지원

## 6. 교훈

- 기기명 기반 적합성 판단은 불충분 → 런타임 지연 모니터링 필수
- undershoot 방지도 정확한 대역폭 추정에 overshoot 방지만큼 중요
- 저복잡도 인코딩 + 비대칭 코덱 조합으로 AV1 적용 기기 대폭 확대

## 7. 설계 의도: 하위 호환을 버린 것인가

- 아님. AV1 은 가능한 기기에서만 쓰고 나머지는 H.264 를 유지
- 근거: 소프트웨어 인코더 자체 개발, 코덱 전환, 비대칭 코덱, 런타임 지연 모니터링
- 목적은 저대역 화질 개선으로 보임
- 하드웨어 AV1 보급을 향후 과제로 두었으므로, 지금은 소프트웨어 처리와 폴백으로 버티고 보급되면 적용 범위를 넓히려는 방향으로 읽힘
- Meta 내부의 정확한 의사결정 배경은 공개되지 않음

## 8. 향후 계획

- 그룹 통화로 확대 (다수 스트림 동시 디코딩이 걸림돌)
- 전 기기 등급에서 하드웨어 AV1 지원
- AV1 트래픽 증가에 따른 ML 모델 지속 개선
