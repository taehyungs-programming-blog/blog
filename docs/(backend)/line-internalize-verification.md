# 기획서 없이 내재화하기: 검증 로직으로 동일함을 증명하다 정리

- 출처: [기획서 없이 내재화하기: 검증 로직으로 동일함을 증명하다](https://techblog.lycorp.co.jp/ko/internalizing-without-specification-proving-equivalence-through-verification-logic)
  (LINE Plus Global E-Commerce 팀)

## 1. 배경

- 외부 시스템에 의존하던 모듈을 자체 시스템으로 내재화
  - 카탈로그 조회 API
  - 카탈로그 통계 업데이트 로직
  - 판매자 상품 수신 파이프라인
- 사양서·기획서 없음, 일부는 소스 코드도 볼 수 없는 블랙박스
- 규모: 카탈로그 수천만 건, 상품 수억 건, 수신 스케줄 하루 수백 회
  - 사람이 수동 비교할 수 없는 규모

## 2. 문제

- "신규 코드가 기존과 동일하게 동작하는가"를 증명해야 함
- 응답 필드 100개 이상, 필터·정렬 조건이 얽혀 있음
- 정렬 기본 처리, API 기본값 등 명세에 없는 동작 존재
- 리팩토링 중 기존 트리거가 누락될 위험

## 3. 핵심 접근: 입력/출력 정의 + 검증 루프

| 구분 | 내용                                            |
| ---- | ----------------------------------------------- |
| 입력 | 동일 ID, 동일 시점 스냅숏, 동일 상품 파일       |
| 출력 | API 응답 객체, DB 업데이트 결과, 최종 등록 상품 |

검증 루프 4단계:

1. 트리거: DB 변경 / 개발자 요청 / 파일 수신 → Kafka 전파
2. 실행·비교: 같은 입력을 기존·신규에 주입 후 비교
3. 가공·적재: 불일치를 통계화 → 알림 / 저장소 적재
4. 분석·개선: 패턴 분석 후 수정, 차이 0까지 반복

```text
[CDC / 요청 / 파일] → Kafka → 검증기 ─┬→ 기존 시스템
                                      └→ 신규 시스템

비교 결과 → Kafka → OpenSearch / ksqlDB → Slack
```

## 4. 검증 대상별 구조

### 4-1. 조회 로직 (API)

- CDC로 카탈로그 DB 변경 감지 → 기존·신규 API 듀얼 호출
- 응답을 `Map<String, Object>`로 변환 후 재귀 탐색, Key 기준 값 비교
- 1차 비교 실패 시 정렬 후 2차 비교
  - 로직 결함과 단순 순서 차이를 구분
- 기본값이 어디서 채워지는지 대조 과정에서 역추적
- 필드당 분당 추출 건수 제한(rate limit)으로 노이즈 제어
- 응답 시간도 기록해 성능 개선을 수치로 확인
- 불일치 → Kafka → OpenSearch 적재, ksqlDB 집계 → Slack 알림

### 4-2. 업데이트 로직 (통계)

- CDC 이벤트 발생 시 신규 로직이 예상값 계산
  → 기존 로직이 DB에 쓴 실제값과 대조
- 비동기 시차 대응
  - 통계와 무관한 변경은 필터링
  - 불일치 시 재시도 큐로 보내 N회 재확인, 그래도 다르면 실제 차이
- 기존 스트림에 붙이지 않고 별도 프로세스로 운영 (부하 우려)
- ETL 배치 전수 조사
  - Iceberg 테이블로 하루 1회 전체 카탈로그 통계 비교
  - 실시간 검증에서 놓친 **트리거 누락**을 여러 건 발견

### 4-3. E2E (수신 파이프라인)

- 쉐도우 파이프라인: 신규를 병렬 실행, 결과는 별도 저장소에 적재
- 스냅숏 키: `SKU + merchantUpdateDate` → 같은 파일의 산출물 특정
- 확인된 사양 차이·불필요 필드는 비교 제외
- 스케줄 단위로 유효 건수, 오류 건수, 단계별 상태 비교
- 매칭 기준은 시스템 ID가 아닌 **원천 소스 URL**
- 전부 일치 시 성공, 하나라도 다르면 상세 링크 포함 Slack 알림

## 5. 디버깅 도구

- OpenSearch 대시보드
  - 일치율 추이, 오류 유형·필드별 그룹화, 시계열 이상 감지
  - 타입 변환 오류 1건이 수십만 건 노이즈를 만드는 경우도 쉽게 발견
- 검증 전용 admin 페이지
  - 카탈로그 비교: 불일치 빨강, 순서만 다르면 노랑
  - 시뮬레이션: ID 입력 → 신규 통계 실행, 원천 상품·필드 추적
  - 파이프라인 비교 뷰어: 단계별 상태·상품 수 좌우 비교

## 6. 결과

- 수백만 건 오류 로그 → 점차 감소, 일치율 100% 수렴
- 배치 전수 조사로 트리거 누락 보정
- 신규 API가 기존보다 빠름을 응답 시간으로 확인

## 7. 교훈

- 블랙박스여도 입력/출력을 정의하고 문제를 쪼개면 동일성 증명 가능
- 실시간 검증 + 배치 검증을 함께 써야 서로 놓치는 결함을 잡음
- 시각화·admin 도구는 초기에 만드는 것이 장기적으로 효율적
